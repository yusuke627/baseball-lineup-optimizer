# 検証結果

この文書は、打順シミュレーターの計算と選手データ、画面が正しく動いているかを確かめた結果をまとめたものです。計算の方式や設計の理由は [`DESIGN.md`](DESIGN.md) を参照してください。

用語：「選手データ」は、あらかじめ用意した選手の打撃成績です（コードと API では preset と呼びます。ファイルは `data/presets/`、API は `GET /presets`）。「案A」はマルコフ連鎖による厳密計算、「案B」はモンテカルロシミュレーションです。

## 1. 方針と実行方法

計算の正しさは、自動テストと、別の方式・公開値との突き合わせの2つで確かめています。この章では、テストの実行方法と、テストが何を確かめているかを示します。

バックエンドのテストは `backend/` で実行します（テストは `from app...` で読み込むため）。

```bash
cd backend
pytest -v
```

フロントエンドのテストと配色の検査は `frontend/` で実行します。

```bash
cd frontend
npm ci
npm run test       # 画面の部品と操作のテスト（Vitest）
npm run contrast   # 文字と部品のコントラスト比の検査
```

## 2. 確率の整合性と単調性

モデルの土台となる遷移確率が確率として正しいこと、成績を良くしたときに期待得点が論理的に正しい向きへ動くことを確かめました。

- `test_transition_probabilities.py`：任意の打者のイベント確率について、24個のすべての（走者状況, アウト数）の状態から出る遷移確率の合計が 1.0 になる（誤差 1e-9 以内）→ **PASS**
- `test_transition_rules.py`：11種類のイベント × 24状態のすべての分岐で、次の3つを確かめる → **PASS**
  - 分岐の確率の和が 1（誤差 1e-12 以内）
  - （遷移前の走者の数 ＋ 打者）＝（遷移後の走者の数 ＋ 得点 ＋ 増えたアウトの数）。塁は走者1人分の有無で表すため、2人が同じ塁に置かれると走者が1人消えて、この式が成り立たなくなる。そのため、この確認で塁の重なりも見つけられる
  - 犠打（S3・S13・S23・S123）と、一・二塁と満塁での単打の遷移が、期待する表（DESIGN.md 3-3）と一致する
- 遷移ルールの修正：このテストを作る前の実装では、走者の数が保存されない分岐が12ありました（犠打で、三塁走者が生還したのに三塁に走者が残る分岐が6、単打で、二塁走者が三塁で止まったときに一塁走者も三塁まで進み、2人が重なって1人が消える分岐が6）。この2つを直し、11種類のイベントすべてで保存が成り立つことを確かめました。修正前のコードに対しては、このテストのうち20件が失敗します
- `test_monotonicity.py`：
  - 本塁打の確率を +5ポイント、アウトの確率を −5ポイントにすると、1試合の期待得点が増える → **PASS**
  - 四球の確率を +5ポイント、アウトの確率を −5ポイントにすると、1試合の期待得点が増える → **PASS**
  - 三振の確率を +5ポイント、単打の確率を −5ポイントにすると、1試合の期待得点が減る → **PASS**

## 3. 案Aと案Bの突き合わせ

同じ遷移ルールを使う2つの方式（案A：厳密計算、案B：乱数による試行）が、同じ入力で近い値になることを確かめました。盗塁なしと盗塁ありの両方で比べています。

### 3-1. 盗塁なし

`test_ab_convergence.py`：9人とも同じ「平均的な打者」のイベント確率（テストの中で決めた値。特定の年のリーグ平均ではない）を使いました。

- 案A：**4.0900 点/試合**（乱数を使わないため、環境によらず同じ値）
- 案B：3万試行を、10通りのシード（1〜10）で測定

| | 値（点/試合） | 案Aとの相対誤差 |
|---|---|---|
| 10シードの平均値の平均 | 4.0953 | +0.13% |
| 最小（seed=5） | 4.0740 | −0.39% |
| 最大（seed=8） | 4.1305 | +0.99% |
| 相対誤差の絶対値の平均 | — | 0.32% |

- 10シードすべてで、許容の基準（相対誤差 3%以内）を満たしました。テスト（seed=42。4.0843）も **PASS** です
- 1試行あたりの得点の標準偏差は約 2.96〜3.02 点/試合で、3万試行の平均の標準誤差は約 0.017点（案Aの約0.4%）です。最大の +0.99% はその約2.4倍で、シードによってこの程度のばらつきが出ます
- 特定のシードの値は、Python や numpy などの版によって変わり、再現しないことがありました（遷移ルールの修正前の実装で、seed=42 の値が、記録の無い環境では 4.0428、10章の環境では 4.0550。原因は特定していません）。そのため、この章では特定のシードの値ではなく、複数のシードの分布で評価しています
- 遷移ルールの修正（2章）の前の実装では、案A 4.0607、10シードの平均値の平均 4.0663（+0.14%）、最小 4.0438（−0.42%）、最大 4.1030（+1.04%）、相対誤差の絶対値の平均 0.33% でした（10章の環境で再計算して確認）

### 3-2. 盗塁あり

3-1 と同じ「平均的な打者」9人に、盗塁の確率を与えて比べました。

| 条件 | 案A | 案B | 相対誤差 |
|---|---|---|---|
| 9人とも 企図率0.2・盗塁死率0.3（3万試行, seed=42） | 4.0319 | 4.0507 | 約0.5% |
| 1・2番だけ 企図率0.3・盗塁死率0.2、ほかは盗塁なし（20万試行, seed=42） | 4.1040 | 4.1039 | 約0.0%（−0.002%） |

- 1行目は、9人の盗塁確率が同じなので、案Aの近似（一塁走者を「直前の打者」とみなす。DESIGN.md 参照）による誤差が生じない条件です。許容の基準（3%以内）を満たします（テストで確認）
- 2行目は、盗塁確率が打者ごとに違う条件で、案A（近似）と案B（一塁走者本人を追跡）の差を参考として測りました。差 −0.0001点は、案Bの標準誤差（約 0.0066点＝標準偏差 2.97 ÷ √200,000）の範囲内で、この条件では近似の影響は検出できないほど小さい結果でした
- 1行目の盗塁死率 0.3 は損益分岐（成功率7割前後）の付近のため、盗塁なし（4.0900）より期待得点がわずかに下がっています
- 遷移ルールの修正（2章）の前の実装では、1行目が 4.0050／4.0174（約0.3%）、2行目が 4.0760／4.0807（約0.1%、差 0.0047点、標準誤差 約0.0066点＝標準偏差 2.95 ÷ √200,000）でした（10章の環境で再計算して確認）

## 4. 既知の得点水準とのベンチマーク

モデルが、常識的に妥当な範囲の値を出しているかを、粗く確かめました。

`test_benchmarks.py`：概算の「平均的な打者」（打率 .245 前後、出塁率 .330 前後を想定したイベント確率。特定の年のリーグ平均そのものではない）を9人並べた場合の1試合の期待得点が、テストの合否の範囲 **3.5〜5.5 点/試合** に入ることを確かめています。

- 算出値：**4.0900 点/試合**（143試合に換算すると約 584.9点）→ **PASS**（遷移ルールの修正前の実装では 4.0607 点/試合、約 580.7点）
- 3.5〜5.5点はテストの合否の範囲で、出典のある値ではなく、広めに置いた幅です
- 実際のMLBの平均得点との比較は行っていません
- 実際の得点は、相手投手の力量やパークファクターなど、モデルの外の要因にも左右されます。このベンチマークは、桁や大きさが妥当かを見る粗い確認です

## 5. 2003年の得点期待値表（RE24）との照合

公開されている得点期待値表（走者とアウト数の24状態ごとの期待得点）と、モデルの値を比べました。進塁確率・打者成績・比較対象の表を、すべて同じ年（2003年シーズン）にそろえています。

この章の数値は、遷移ルールを修正した（2章。犠打と単打の走者の扱い）今の実装で計算したものです。修正前の遷移での値も併記します。修正前の遷移で同じ手順を計算すると、修正前に記録していた値（MAE・バイアス・満塁1アウトの差）をすべて再現できたので、手順が同じであることを確かめたうえで、修正後の遷移に当てています。

### 5-1. 年代をそろえた理由

年代の異なる得点期待値表（1963年、2008年、2012年、2010〜2015年など）や、架空の近似値の打者確率と比べると、「モデルが正しいか」と「年代や打者の違いによるずれ」を切り分けられません。そのため、出典と年代をそろえて比べました。

### 5-2. 方法

- **記事**：James Click「Run Expectancy Matrix and base-advancement rates (2003 MLB season data)」（Baseball Prospectus、2004年5月6日掲載。2003年シーズンの数値）。以下「2004年掲載の記事（2003年シーズンの数値）」と呼びます
- **進塁確率**：2004年掲載の記事（2003年シーズンの数値）の値（実装の `DEFAULT_ADVANCE_PROBS` と同じ）
- **比較対象の表**：同じ記事に、2003年シーズンの数値として載っている RE24 表。表の24個の数値は、作者が記事から転記したもので、この文書には載せていません
- **打者成績（計算側の入力）**：Lahman Baseball Database（`data/raw/lahman/Batting.csv`）の、2003年の全選手の打撃成績の合計。同じデータベースの `Teams.csv` の2003年の30球団の合計と、AB・H・2B・3B・HR・BB・SO・HBP・SF・SB・CS・R がすべて一致しました（空欄はありません）。この合計が Baseball-Reference のチーム打撃成績の合計と同じかは、**未確認**です
- **イベント確率**：アプリと同じ方法（`metrics.event_probabilities`。DESIGN.md 3-2）で、リーグ全体の合計から求めます。打席数は AB + BB + HBP + SF + SH ＝ 187,437。四球（BB）は敬遠を含む値のまま使います
- **比べる値**：同じリーグ平均の打者が打ち続けたときの、24状態それぞれからイニングの終わりまでの期待得点（案Aと同じ吸収マルコフ連鎖を、打者1人分の遷移行列で解いた値）。MAE は24状態の誤差の絶対値の平均、バイアスは誤差（モデル − 表）の平均
- **0.651 の補正の当てはめ方**：凡退（OUT）で、三塁に走者がいるときだけ、三塁走者が確率 0.651 で生還するとします（2アウトでの凡退は3アウトで終わるので、生還しません）。三振や併殺打にも当てると、修正前に記録していた値と一致しませんでした（例：凡退と三振に当てると、修正前の遷移で MAE 0.0494）

これにより、進塁確率・打者成績・比較対象の表のすべてが、2003年シーズンという同じ年代にそろいます。計算はすべて案A（乱数を使わない厳密計算）で行いました。

### 5-3. 結果

| | MAE | バイアス | 満塁・1アウトの差 |
|---|---|---|---|
| 打球アウトでの進塁を考慮しない場合（今の実装） | 0.1158点 | −0.1026点（系統的に過小評価） | −0.0440点 |
| 打球アウトでの三塁走者の生還（確率 0.651）を加えた場合（検証の実験だけ） | **0.0357点** | **+0.0145点** | +0.2214点 |
| （修正前の遷移での値）考慮しない場合 | 0.1195点 | −0.1086点 | −0.0603点 |
| （修正前の遷移での値）0.651 を加えた場合 | 0.0369点 | +0.0088点 | +0.2053点（約 +0.21点） |

- 遷移ルールの修正による24状態の期待得点の変化は、一・二塁と満塁の状態で大きく、最大で +0.03点程度です（例：0アウト満塁は 2.0943 → 2.1240）。ほかの状態の変化は、それより小さいです

補正に使った **0.651 は、この検証で調整した値ではありません**。比較対象の表と同じ、2004年掲載の記事（2003年シーズンの数値）に載っている定数です（原文：".651 = Runner scores from third on any ball in play"。記事の中のほかの6つの定数と同じ一覧にあります）。

打球アウトでの進塁を1点だけ補正すると、MAE は 0.1158 から 0.0357 に縮み、系統的な過小評価もほぼなくなりました。観測された過小評価の大部分が、この簡略化で説明できることと整合します。ただし、次の点に注意が必要です。

1. この定数の定義は「任意のボールインプレーでの三塁走者の生還率」で、ヒットを含みます。検証では打球アウトにだけ当てはめたため、アウトだけの生還率としては過大な近似になっている可能性が高いです
2. 取得できた範囲では、記事はこの定数の当てはめ方を説明しておらず、検証での当てはめ方は本プロジェクトの仮定です
3. 定数と比較対象の表が同じ出典で、第三者のデータによる独立した検証ではありません
4. 満塁・1アウトなどで、誤差が残っています（5-4）

**補正値を動かした場合**：今の実装で、同じ当てはめ方（凡退で三塁に走者がいるとき）のまま、補正値を 0〜1 の範囲で 0.001 刻みに動かしました。MAE が最小になるのは **0.677**（MAE 0.0353点、バイアス +0.0185点、満塁・1アウトの差 +0.2320点）で、0.651 のとき（MAE 0.0357点、バイアス +0.0145点）との差は小さいです。0.665〜0.695 の範囲では MAE はほぼ同じ（小数第4位で 0.0353）です。バイアスが 0 に最も近いのは 0.559（MAE 0.0392点）です。この最適値は、比較対象の表に合わせて選んだ値なので、独立した検証の結果ではありません。アプリのコードと設定は変えていません。

この結果は、打球アウトでの進塁を扱っていないことが誤差の主な原因らしいことを示す**診断**として位置づけ、本番のコード（`DEFAULT_ADVANCE_PROBS`・`resolve_event`）には入れていません。定数の定義が「任意のボールインプレー」で、アウトだけに当てはめると近似にとどまること、また二塁→三塁・一塁→二塁などのほかの進塁打も欠けていて、それと打ち消し合っている可能性があることが理由です。

### 5-4. 残った誤差についての考察

5-3 の補正（0.651）の後も、満塁・1アウトの状態で +0.22点（+0.2214点。修正前の遷移では +0.21点）の過大評価が残りました。原因について、次の仮説を記録します（検証していない仮説で、実装は変えていません）。

**仮説：併殺の確率が、状況によらず一律（シーズン平均）になっているため**

モデルの併殺（GIDP）の確率は、シーズンの全打席に対する併殺打の割合をそのまま使っています。これは、併殺が起こりうる場面（一塁に走者がいる）と起こりえない場面（一塁に走者がいない）を区別せずに平均した値で、併殺が起こりうる場面に限った割合は、シーズン平均よりかなり高くなります。

満塁は、一塁に走者がいて併殺が起こりうる状況ですが、モデルはここでも薄められたシーズン平均の確率しか併殺に割り当てず、残りの確率の大部分を通常のアウト（5-3 の「打球アウトでの三塁走者の生還（0.651）」の対象）に振り分けます。その結果、本来は併殺になるはずの打席の一部が「三塁走者が生還するアウト」として扱われ、期待得点を余分に押し上げていると考えられます。

この仮説は、過大評価という向きとは整合しますが、これだけで +0.22点のずれをすべて説明できるかは確かめていません。満塁に特有の守備の判断（本塁で封殺するか、併殺を優先するか）など、ほかの要因が残っている可能性もあります。また、5-3 の注意点1のとおり、ヒットを含む定義の 0.651 を打球アウトだけに当てはめたこと自体も、過大評価の向きに働きえます。

この仮説への対処（状況別の併殺の割合を別にモデル化するなど）は、文献に基づく進塁確率を変えることとは別の話です。ここでは考察にとどめ、`DEFAULT_ADVANCE_PROBS` などの既存のパラメータは変えていません。今後の拡張の候補として検討します。

### 5-5. 誤差は統計的なぶれではない

この検証は、すべて案A（乱数を使わない厳密計算）で行いました。そのため「試行回数を増やせば真の値に近づく」という考え方は当てはまりません。観測されたずれは、モデルの前提（状況によらない確率の適用、一部のプレーを扱っていないこと）によるもので、統計的なぶれではありません。

### 5-6. 行っていない照合

Bukiet, Harold and Palacios (1997) や D'Esopo and Lefkowitz (1977) などの先行研究に載っている、具体的な打線・チーム単位の計算例との直接の照合は、行っていません。ただし、5章の「年代をそろえた24状態の得点期待値表との比較」は、それより網羅的で定量的な検証で、優先して行う価値があったと考えています。

## 6. 盗塁の組み込みの検証

盗塁（一塁→二塁）を案A・案Bの両方に組み込んだことについて、組み込みが正しいことと、選手データから求める盗塁の確率を確かめました。

### 6-1. テスト

`test_steals.py`：

- 盗塁の確率がすべて 0 なら、案Aの値が盗塁なしのモデルと一致する（誤差 1e-12 以内）→ **PASS**
- 盗塁のステップ（打席の前に挟む処理）の遷移行列の各行の和が 1 になる → **PASS**
- 必ず成功する盗塁を加えると期待得点が増え、必ず失敗する盗塁を加えると減る → **PASS**
- 盗塁企図率が (SB+CS) ÷ (単打+四球+死球) で算出される → **PASS**

案Aと案Bの突き合わせ（盗塁あり）は 3-2 を参照してください。

## 8. 計算速度の測定

推奨打順の探索と API の計算にかかる時間を測りました。高速化の方法（遷移行列のキャッシュ、OpenBLAS のスレッド数）は DESIGN.md 4-2 を参照してください。

条件（特に書いていない限り）：10章の環境（Intel Core Ultra 7 265・論理 CPU 20、Windows 11、Python 3.13.14、numpy 2.4.4・OpenBLAS 0.3.31）、`OPENBLAS_NUM_THREADS=1`（app の既定値。環境変数が1であることを確かめた）、遷移行列のキャッシュあり。今の実装（2章の遷移ルールの修正の後）で測りました。

### 8-1. 全打順の探索

- 9人の全打順（9! = 362,880通り）を厳密に探索する関数（`find_optimal_lineup`）：**454.4秒（約7.6分）**
- 打者は `test_optimizer.py` と同じ多様な9人、盗塁の確率は照合済みの2選手（Judge・Arraez）の値を交互に設定（API と同じく盗塁あり）。遷移行列は打者9件・盗塁2件を構築し、以降はすべて再利用。1回だけの測定
- 求めた最良の打順の期待得点は 3.678717 点/試合
- 修正前の実装で測った値は 512.1秒（約8.5分。同じ条件で1回だけの測定）。短くなった理由は**未確認**です。どちらも1回だけの測定です
- この時間は API の応答としては長すぎるため、API では多点の山登り法で推奨打順を求めています（DESIGN.md 4-1）

### 8-2. 高速化の効果

- 216×216 の逆行列の計算1回（`I − Q` に近い正則な行列。準備に5回計算したあと、200回の中央値）：OpenBLAS の既定のスレッド数で **44.40ミリ秒**（最小 4.49、最大 95.71）、1スレッドで **0.59ミリ秒**（最小 0.56、最大 0.64）。スレッド数は、numpy だけを読み込む別々のプロセスで、環境変数 `OPENBLAS_NUM_THREADS` を設定する・しないで切り替えた

- 計算結果への影響：キャッシュあり（`adv` を省略）と、なし（`adv` に既定値のコピーを渡す）とで、案Aの期待得点の差は **0**（Judge・Arraez の打者で、シード16で選んだ16通りの打順 × 盗塁なし・あり。盗塁の遷移行列は、どちらもキャッシュを通る）

高速化の前後の比較（修正前の実装で測った値。テスト一式（24件）と、改善前・キャッシュのみの構成は、今は用意できないため測り直していません）：

### 8-3. 計算の軽量化（案Aの評価、探索、案Bの試行回数）

公開先の CPU が小さいため、計算を軽くしました（DESIGN.md 4-2 の3・4、3-6）。この節の時間は、軽量化の前後を、同じ入力で手元で測った値です。

- B：1回の探索の中で、同じ打順の評価を使い回す
- C：案Bの試行回数を 1000 にする（環境変数 `MONTE_CARLO_TRIALS`。公開用のイメージの設定）

条件：10章の環境、`OPENBLAS_NUM_THREADS=1`、遷移行列のキャッシュあり、盗塁あり。推奨打順の探索（`multi_restart_hill_climb`）の乱数のシードを 2025 に固定し、探索の時間と案Bの時間を、それぞれ3回測った中央値です（リクエストの処理のうち、ほかの部分は 0.01秒未満のため含めていません）。

- 選手データ9人の選び方：Judge・Arraez に、ほかの7人をシード1で選んだもの。ランダムな9人は、選手データからシード3で選んだもの
- 結果への影響：どちらの打線でも、軽量化の前後で推奨打順は同じでした。推奨打順の期待得点の差は最大 2.7e-15、入力打順の期待得点の差は最大 8.9e-16 です（浮動小数点の丸めの範囲）
