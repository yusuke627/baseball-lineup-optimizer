# 野球打順最適化アプリ 設計仕様書

## 0. 概要

MLBの実データ（打撃成績）を用いて、任意の打順9人分から得点期待値を計算し、
「①ユーザーが入力した打順の得点期待値」と「②打順の探索により求めた推奨打順とその得点期待値」
を比較表示するアプリケーション（画面では、探索で求めた打順を「推奨打順」と呼ぶ。近似探索のため、最も期待得点が高い打順とは限らないため）。就活ポートフォリオとしてGitHubに公開することを想定する。

### アプリの使い方（基本フロー）

1. **選手情報の入力**：手入力 or プリセット選択の2パターンで9人分の打撃成績を用意する
2. **打順の並び替え**：入力した9人を好きな順に並べる
3. **結果出力**：
   - a) 入力した打順の得点期待値
   - b) 推奨打順（打順の探索で求めた、期待得点が高くなる打順）とその得点期待値
   - c) 上記a, bの差から算出した「非効率%」

## 1. 得点期待値の算出方式

2方式を両方実装する。使い分け（UI上でどちらを使うか、両方出すか）は実装フェーズで別途決定する。

### 状態空間（A・B共通）

走者状況（8パターン）× アウトカウント（0/1/2）＝ 24状態 ＋ 3アウト到達（吸収状態）＝ 計25状態。

| 走者状況コード | 意味 |
|---|---|
| S0 | 走者なし |
| S1 | 一塁のみ |
| S2 | 二塁のみ |
| S3 | 三塁のみ |
| S12 | 一・二塁 |
| S13 | 一・三塁 |
| S23 | 二・三塁 |
| S123 | 満塁 |

状態は `(走者状況, アウト数)` の組で表現する（例：`(S12, 1)` = 一二塁・1アウト）。

### イベント別の遷移ルール

| イベント | 遷移ルール |
|---|---|
| 四球・死球 | 押し出しが発生する状況以外は打者一塁へ。押し出し可能な走者のみ進む（決定的） |
| 単打 | 打者は一塁へ。二塁走者は生還/三塁停止、一塁走者は三塁進塁/二塁停止をアウト数別の確率で分岐 |
| 二塁打 | 打者は二塁へ。三塁・二塁走者は生還、一塁走者は生還/三塁停止をアウト数別の確率で分岐 |
| 三塁打 | 全走者生還、打者は三塁へ（決定的） |
| 本塁打 | 全走者＋打者が生還（決定的） |
| 三振 | 走者は動かずアウト+1 |
| 凡退（三振以外） | 走者は基本動かずアウト+1（併殺は別枠） |
| 併殺打(GIDP) | 一塁走者ありの状況限定。打者アウト＋一塁走者アウト、アウト+2 |
| 犠飛 | 三塁走者ありの状況で発生。打者アウト、三塁走者生還 |
| 犠打（成功のみモデル化） | 打者アウト＋1、走者は全員1つずつ進塁 |

進塁確率（p, q, r等）は**アウト数ごとに別の値**を持たせる（0-1アウト時と2アウト時で走者の積極性が変わるため）。

### 盗塁の組み込み

一塁に走者がいて二塁が空いている状態（`(S1, アウト数)` および `(S13, アウト数)`）でのみ、打者の打席処理の**前**に追加ステップを挟む（実装: `transitions.apply_steal_step`）。一・二塁（S12）など二塁が埋まっている状態の重盗は対象外。

1. 一塁走者の盗塁企図率で「企図する/しない」を分岐
2. 企図した場合、その走者の盗塁成功率で「二塁へ進む（アウト変わらず）」か「盗塁死（アウト+1）」を分岐
3. 盗塁死で3アウトになった場合、打席の打者は打席を完了していないため、次のイニングはその打者から始まる

**一塁走者の特定方法（案A・案Bで異なる）**

- 案A：状態に走者個人を持たないため、打者kの打席前の一塁走者を「直前の打者k-1」とみなし、その打者の盗塁確率を使う近似を行う。一塁走者が2〜3人前の打者である場合（後続打者が走者を動かさずにアウトになった場合など）に誤差が生じる
- 案B：一塁に到達した打者（四球・死球・単打）を追跡し、走者本人の盗塁確率を使う

9人の盗塁確率が同一なら両者は一致する。異なる場合の差は VALIDATION.md 6章を参照。

**盗塁企図率・成功率の算出**（`metrics.steal_probabilities`）

- 企図率 = (SB + CS) ÷ (単打 + 四球 + 死球)。一塁に出塁した回数を盗塁機会とみなす（1.0で上限）
- 盗塁死率（企図あたり） = CS ÷ (SB + CS)

企図率は「一塁に出塁した回数あたり」の値だが、モデルでは「一塁走者がいる打席ごと」に適用するため、一塁に滞在したまま複数打席を迎える場合は企図回数がやや過大になりうる。また、失策・野選での一塁到達は機会に含めていない。

三盗・本盗は対象外（後述の限界事項）。

### 案A：マルコフ連鎖（吸収連鎖）による厳密計算

- 打者ごとの遷移行列を、打順順に9イニング分（実際には「1番→9番→1番…」と打順が継続する形で）掛け合わせ、1試合の得点分布・期待値を解析的に求める。
- 乱数を使わないため決定論的。計算コストが軽い。

### 案B：モンテカルロシミュレーション

- 同じ状態モデルを使い、乱数でイベントを1つずつ引きながら試合・シーズンを多数回試行し平均得点を求める。
- 試行回数を増やせば案Aの厳密値に収束するはず（→検証に利用）。
- 得点の分布（最良・最悪ケースの幅）も出せる。

## 2. 入力データ設計

### 2-1. 手入力モード

ユーザーはイベント確率ではなく、一般的なカウント統計を入力する。

| 項目 | 説明 |
|---|---|
| 打席数 (PA) | 入力必須（1以上） |
| 打数 (AB) | |
| 安打 (H) | |
| 二塁打 (2B) | |
| 三塁打 (3B) | |
| 本塁打 (HR) | |
| 四球 (BB) | |
| 死球 (HBP) | |
| 三振 (SO) | |
| 犠飛 (SF) | |
| 犠打 (SH)（任意） | |
| 併殺打 (GIDP) | |
| 盗塁 (SB) | |
| 盗塁死 (CS) | |

犠打 (SH) は省略可能（省略時は 0）。それ以外の項目は API（`POST /lineup/evaluate`）で入力必須。内部で以下を計算する（`metrics.event_probabilities`）。

- 単打数 = 安打 − 二塁打 − 三塁打 − 本塁打
- 打席数(PA)：入力値をそのまま使う
- 各イベント確率 = イベント数 ÷ PA（端数を調整して合計を1に正規化）

以前は「PA に 0 を入力すると 打数＋四球＋死球＋犠飛＋犠打 で自動計算する」挙動があったが、廃止した。入力フォームで PA を必須にする方針と揃えるためと、PA とすべての成績が 0 の入力でサーバーエラー（500）になっていたためである。

**入力検証**（`backend/app/schemas/batter.py`。フロントエンドの入力フォームも同じルールで検証する）

| 区分 | ルール |
|---|---|
| エラー（API は 422 を返す） | 各成績は 0 以上 20000 以下の整数／PA は 1 以上／AB ≤ PA／H ≤ AB／2B + 3B + HR ≤ H／SO + GIDP ≤ AB − H |
| 警告（計算は行い、レスポンスの `warnings` で知らせる） | AB + BB + HBP + SF + SH が PA と一致しない／PA が 200 未満（標本が小さい） |
| エラー（API は 400 を返す） | `input_order` が `batters` の ID と一致しない／9人でない／重複がある |
| エラー（API は 422 を返す） | `n_games` が 1〜200 の範囲外／打者 ID が空または65文字以上 |
| エラー（API は 422 を返す） | `display_names`（任意）の表示名が、前後の空白を除いて空または41文字以上／制御文字（改行・タブなど）を含む |
| エラー（API は 400 を返す） | `display_names` のキーが `batters` の ID と一致しない／前後の空白を除いた表示名に重複がある |

- 上限の 20000（各成績）と 200（`n_games`）は、統計的な根拠のある値ではなく、誤入力や悪用を防ぐための安全上の上限である
- PA と内訳の合計の不一致をエラーにしないのは、不一致でも計算はできる（イベント確率は合計1に正規化する）一方で、入力ミスの可能性やモデルの前提との関係を利用者に知らせる必要があるため
- PA が 200 未満の打者には、「標本が小さいので、確率の見積もりが実力からずれやすく、打順の結果も変わりやすい」という注意を出す。計算は止めない。**200 という値は本プロジェクトの目安であり、出典・統計的根拠はない**（何打席あれば十分かを示す値ではない）。値はバックエンドの定数 `LOW_PA_THRESHOLD`（`backend/app/schemas/batter.py`）の1か所で決めており、注意文の中の数字もこの定数から作る。この注意は API だけが出し、フロントエンドは基準値を持たない
- バックエンドとフロントエンドの検証ルールの一致は、共通の入力例 `schemas/batter_stats_validation_cases.json` を両方のテストで使って確認する
- リポジトリ内の実プリセットは、すべてのルールをエラー・警告なしで通る（`backend/tests/test_validation.py` で確認）
- フロントエンドの入力フォームは、入力の途中でも、規則ごとに必要な項目がそろえば矛盾を表示する（例：打数と安打だけで H ≤ AB を判定する）。これは画面だけの動作で、全項目を入力した成績に対する結果（有効・無効、警告の有無）はバックエンドと同じである

**打者の ID と表示名**

- 打者 ID（`batters` のキー、`input_order` の要素）は、打者を区別するための内部の値である。画面では枠ごとに固定の ID（`b1`〜`b9`）を使い、利用者には見せない
- 画面に出す名前は、リクエストの `display_names`（打者 ID → 表示名、省略可）で渡す。指定すると、`warnings` の文は打者 ID ではなく表示名で作られる（画面の名前と警告文の名前が食い違わないようにするため）。省略した場合は、従来どおり打者 ID を使う。レスポンスの `input_order`・`best_order` は、常に打者 ID で返す
- 表示名は、前後の空白を除いて1〜40文字（Unicodeの符号位置の数）で、制御文字は使えず、打者同士で重複できない。40文字は画面の表示が崩れないための上限で、長い選手名に、同じ選手を複数の枠に入れたときの番号（「 (2)」など）を付けても収まる長さにしている。画面の既定名は「打者A」〜「打者I」で、空欄にすると既定名に戻す
- 表示名のルールの一致は、共通の入力例 `schemas/display_name_validation_cases.json` を両方のテストで使って確認する
- `GET /presets` の `league` はプリセットのフォルダ名（`data/presets/<league>/`）に使うため、英小文字のみを受け付ける。プリセットJSON内の `"league": "MLB"` とは別の値である

### 2-2. プリセット選択モード

MLB実在選手（実名）の2025年シーズン成績を内蔵データとして用意し、選択するだけで2-1の統計が自動入力される。

**一覧・詳細画面での表示項目**

- 基本表示：打率・本塁打・出塁率・長打率・盗塁数・盗塁成功率（アプリが成績から計算し、`GET /presets` の `summary` として返す）
- 参考値：wOBA・wRC+（プリセットのJSONに公表値が書かれている選手だけ。`GET /presets` の `reference_metrics` として、書かれた値をそのまま返す。無ければ `null`。3-2 を参照）
- 詳細表示（任意展開）：単打数・二塁打数・三塁打数・四死球・三振・犠飛・併殺打数などの内訳と、そこから計算されたイベント確率一覧

**プリセットの API**

| エンドポイント | 返すもの |
|---|---|
| `GET /presets/seasons?league=mlb` | プリセットのあるシーズン（古い順） |
| `GET /presets/teams?league=mlb&season=2025` | 球団の一覧。リーグ（AL・NL）ごとに分け、リーグの中は地区（`division`。東 E・中 C・西 W の順）、地区の中は球団名順。`count` はその球団を最終所属（`team_info.code`）とする選手の数。`team_info` の無いプリセットは `without_team` に数える。地区の無い球団は `division` が `null` で、リーグの最後に並ぶ |
| `GET /presets?league=mlb&season=2025` | 全件（配列）。以前からの呼び出しとの互換のため、形は変えていない |
| `GET /presets?...&team=NYY` | その球団を最終所属とする選手。`{"total": 総数, "items": [...]}`（名前順） |
| `GET /presets?...&q=名前の一部` | 球団に関係なく名前の一部で探す（大文字・小文字とアクセント記号は区別しない）。最大50件と総数（`total`）を返す |

- 移籍した選手は最終所属の球団だけに数え、移籍前の球団の一覧には出ない。名前での検索なら見つかる
- 実データ（348件）で、起動したバックエンドに HTTP で問い合わせて確認した（2026-10-15）：30球団（AL・NL 各15）の選手数の合計は348、`team=NYY` は12人（Judge を含む）、`q=muncy` は2人、`q=jose` は6人（アクセント記号つきの名前を含む）、`q=a` は総数277のうち50件。全件の応答は約298,026バイト、`team=NYY` は約10,227バイト

**画面での選び方**（`frontend/src/components/PresetDialog.tsx`）

- 各カードの「プリセットから読み込む」で、ブラウザ標準のダイアログ（`<dialog>`）を開く。シーズン（既定は最新）→ 球団（リーグ → 東地区・中地区・西地区ごと、地区の中は球団名順、選手数つき）→ 選手（名前順。打率・出塁率・長打率・OPS・本塁打・打席を API の値で表示）の順に選ぶ。名前での検索も使える
- 選手の一覧は、HTML の上では選んだ球団のボタンの直後に置く（ボタンは `aria-expanded` と `aria-controls` で開いた一覧を示す、開閉式の形）。そのため、キーボードでも読み上げでも、球団のボタンの次に選手が続く（ほかの球団のボタンを通らない）。狭い画面ではそのままボタンの下に出し、広い画面では CSS（`position: absolute`）で見た目だけ右側の列に出す。名前での検索の結果は、検索欄の直後に出す
- Esc キーは、ブラウザ標準の動き（`cancel` イベント）に加えて、ダイアログの中で押されたキーも直接受け取って閉じる
- 選手を選ぶと、そのカードに成績14項目と名前を読み込む。入力済みのカードに読み込むときは、プリセットのダイアログの上に確認のダイアログ（`role="alertdialog"`）を重ねて「打者Aの入力を上書きします。よろしいですか？」と確かめる。Esc キーとキャンセルは確認だけを閉じ（プリセットのダイアログは閉じない）、フォーカスを選んでいた選手の「読み込む」ボタンへ戻す。同じ選手を別のカードにも読み込むと、表示名に「 (2)」などを付ける（ほかの打者からのコピーの確認は、従来どおりカードの中に出す）
- カードの上には、選手名・シーズン・球団「球団名 (コード)」、移籍した選手の「年間合計（複数球団）／在籍した球団：TB → CWS」（球団コードで出場した順）を表示する。成績の出典はカードごとには出さず、ページの一番下に常に表示する「データの出典」欄（`frontend/src/components/DataSources.tsx`）にまとめる。欄には、Lahman Baseball Database (SABR) / CC BY-SA 3.0（集計の方法と「第二出典との照合は一部のみ（未確認）」を添える）と、照合済みの2人（Aaron Judge・Luis Arraez）の出典（各ファイルの `source` と同じ値。一致はテストで確認）を並べる。リンクは `https://` で始まる URL だけに付け、新しいタブで開き、`rel="noopener noreferrer"` と読み上げ用の「（新しいタブで開きます）」を付ける。参考値（`reference_metrics`）の出典は、従来どおりカードの参考値の横に出す
- 確認（2026-10-15）：Edge 155（ヘッドレス）を DevTools Protocol でキーボード・マウス操作し、幅 1200px と 600px で、球団を選んだあとの Tab が選手の「読み込む」へ進むこと、Esc で閉じること、確認の Esc が確認だけを閉じてフォーカスが選手へ戻ることを確かめた
- 読み込んだあとに成績を1項目でも変えると「（編集済み）」と表示し、参考値（`reference_metrics`）を隠す。値を元に戻すか「プリセットの値に戻す」を押すと、編集済みではなくなる。表示名は書き換えない。ほかの打者からのコピーで入った成績は手入力の扱い（プリセットの情報や参考値は写さない）
- 表計算ソフトなどからの貼り付けで成績を入れる機能は、導入しない方針とする（2026-10-15 決定）。以前は段階6cとして計画していた。プリセットに無い選手は手入力で入れる
- 2026年のプリセットは無い。2026年を含む Lahman Baseball Database の版が公開されれば、同じ生成スクリプト（2-4）で作れる見込みだが、公開の時期と内容は**未確認**。シーズンの切り替えは、プリセットのあるシーズン（`GET /presets/seasons`）だけを出すので、2026年のデータを `data/presets/mlb/2026/` に置けば、画面と API を変えずに選べるようになるはずである（コードの作りからの見込みで、2026年の実データでは未確認）

**打順の並べ替え**（`frontend/src/components/OrderList.tsx`）

- 画面の「2 打順」で、上から1番〜9番の順に並べ替える。並べ替えた順番が、そのまま計算のリクエストの `input_order` になる。入力の枠（カード）の並びは変わらない
- 操作は3通りで、どれでも同じ結果になる。ドラッグが使えない環境やスクリーンリーダーでも、ボタンと番号の指定だけで全ての操作ができる
  - ドラッグ：各行の取っ手（⋮⋮）を持って動かす。マウス・タッチ（`PointerSensor`）とキーボード（`KeyboardSensor` と `sortableKeyboardCoordinates`。スペースかエンターで持ち上げ、上下の矢印キーで動かし、もう一度スペースかエンターで置く。エスケープでやめる）。操作の説明と、持ち上げ・移動・終了・中止の読み上げは日本語で用意した
  - 「上へ」「下へ」：1つずつ動かす。1番の「上へ」と9番の「下へ」は押せないが、フォーカスはでき、理由（「1番なので、これより上へは移動できません。」など）が読み上げられる（`aria-disabled` と `aria-describedby`）
  - 「移動先」と「移動」：番号（1〜9）を選んで、その番号へ動かす。間の打者は順番を保ったまま詰める
- 並べ替えたあとは、動かした打者の同じ操作にフォーカスを戻し、結果を `aria-live` で「打者Cを3番から1番に移動しました。」の形で知らせる（ドラッグのときは、dnd-kit が同じ内容を読み上げるので、二重にならないよう、こちらでは知らせない）
- 計算したあとに成績・表示名・打順を変えると、前の結果を消し、「前の計算結果は消しました。もう一度『期待得点を計算する』を押してください。」と表示する
- 各行には、`POST /batters/metrics` が返した打者ごとの指標と、その打者についてのすべての注意（打席数が少ない、打席数と内訳が合わない。API の文のまま）を出す。指標は AVG（打率）→ PA（打席）→ H（安打）→ HR（本塁打）→ OBP（出塁率）→ SLG（長打率）→ OPS → K%（三振率）→ BB%（四球率）→ SB（盗塁）の順で、画面には略号を、読み上げには日本語の名前を使う（略号にマウスを重ねると日本語の名前が出る）。計算できない値（null）は「—」。率は「.278」の形、K% と BB% は API が返す割合（0〜1。例：0.215）を「21.5%」の形（小数点以下1桁のパーセント）にする。どちらも表記をそろえるだけで、新しい値は作らない。成績がそろって検証を通った打者だけを送り、入力が落ち着いてから（約0.3秒後）呼ぶ。表示名に問題がある間は、注意の文に正しい名前を出せないので呼ばない。プリセットを読み込んで編集していない打者には、参考値（`reference_metrics`）も出す
- 「計算と結果」の上に、「打席数が少ない打者」の一覧を出す。対象は、API の種類つきの注意（`warning_items`）のうち `code` が `LOW_PA` のものがある打者だけで、文は API のまま出す。基準の打席数（`LOW_PA_THRESHOLD`）や文の内容による判定は、フロントでは行わない
- ドラッグの部品には dnd-kit（`@dnd-kit/core` 6.3.1、`@dnd-kit/sortable` 10.0.0、`@dnd-kit/utilities` 3.2.2。いずれも MIT ライセンス）を使う。採用の理由は、マウス・タッチ・キーボードでのドラッグと、読み上げの仕組みを1つの部品でそろえられるため。peer 依存は `react >=16.8.0` で、React 19.3 で動くことを、実際のブラウザ（Edge 155、ヘッドレス）でキーボード・マウス・タッチの操作をして確かめた（2026-10-15）。導入時の `npm audit` は 0 件
- **注意**：dnd-kit のこれらの版の最終公開は 2024年12月（`@dnd-kit/utilities` は 2023年11月）で、更新が止まっている可能性がある（npm の公開日からの見立て）。後継として `@dnd-kit/react`（0.x）が公開されているが、安定版ではないため使っていない。React の大きな更新のときは、動作を確かめ直す必要がある。ボタンと番号の指定だけで全ての操作ができるので、ドラッグが動かなくなっても並べ替えはできる
- テスト環境（jsdom）は `<dialog>` の `showModal` を実装していないため、テストでは開閉だけを置き換えている。フォーカスの閉じ込めや Esc キーで閉じる動きは、自動テストでは確認していない

打点(RBI)は表示しない。前の打者の出塁状況に大きく左右される文脈依存の指標で、モデル計算にも使わないため、プリセットデータにも含めない。

### 2-3. プリセットデータのファイル設計（管理者が追加しやすい形）

1選手＝1レコードのJSONファイルとして管理し、管理者はファイルを追加するだけで新規選手を追加できる。

```
data/presets/mlb/2025/
  ├── shohei_ohtani.json
  ├── mookie_betts.json
  └── ...
```

各JSONは「カウント統計＋メタ情報（年度・出典URL・取得日）」を保持し、打率・出塁率・長打率などの表示用指標は**アプリ側が自動計算**する。wOBA・wRC+ はアプリでは計算しないので、表示したい場合だけ、公表値を任意の `reference_metrics` 欄に書く（3-2）。JSON Schemaを1つ定義し、新規ファイルはCIでバリデーションする。年度・リーグ別にディレクトリを分けておくことで、将来的な拡張（他年度・他リーグ）にも対応しやすくする。

**NPBのプリセットについて**：NPBのプリセットは、今は提供しない。また、架空の名前のプリセットは作らない（実在の選手の成績に別の名前を付けたものも、架空の選手の成績も作らない）。いずれも、リスクを避けるため。

### 2-4. Lahman からの生成方針

プリセットを数百件の規模に増やすため、Lahman Baseball Database の CSV からプリセットを作るスクリプト `scripts/build_lahman_presets.py` を用意している。`--dry-run`（集計して報告するだけ）、`--sample`（固定のシードで選んだ選手の成績を表にするだけ）、`--generate`（プリセットの JSON を作る）、`--names-only`（既存のプリセットの `name` だけを、表示名の上書きに合わせて書き換える。下の「名前の接尾辞」）の4つの使い方がある。

- 元データ（`Batting.csv`・`People.csv`・`Teams.csv`）は利用者がダウンロードして `data/raw/lahman/` に置く。スクリプトはネットワークから取得しない。`data/raw/` は `.gitignore` でリポジトリから除外している。使ったのは「The SABR Lahman Baseball Database 1871-2025」（readme の記載で Release Date: Dec 10, 2025）
- ライセンス：readme には「This database is copyright 1996-2025 by SABR, via generious donation from Sean Lahman.」「This work is licensed under a Creative Commons Attribution-ShareAlike 3.0 Unported License.」と書かれている（原文のまま）。コードのライセンス（MIT）とは分け、`data/` 配下のプリセットにだけ適用する方針とする（表示は `data/NOTICE`、README のライセンス欄、画面の「データの出典」欄）
- CSV の形式（2025年版で確認）：`People.csv` と `Teams.csv` は先頭に BOM があり、`Batting.csv` にはない。スクリプトは `utf-8-sig` で読むので、どちらでも列名を正しく読める。列名は `Batting.csv` が playerID, yearID, stint, teamID, lgID, G, AB, R, H, 2B, 3B, HR, RBI, SB, CS, BB, SO, IBB, HBP, SH, SF, GIDP、`People.csv` に nameFirst・nameLast、`Teams.csv` に yearID・teamID・name がある
- 集計：`Batting.csv` の対象シーズンの行を、選手（`playerID`）ごとに合算する（同じシーズンに複数の球団に在籍した場合は、在籍ごとの行＝stint を足す）。合算する列は G, AB, R, H, 2B, 3B, HR, RBI, SB, CS, BB, SO, IBB, HBP, SH, SF, GIDP
- 空欄の扱い：どれか1つの stint で空欄の列は、合計を「欠損」とする（0 とはみなさない）。プリセットに使う項目が欠損している選手は、候補にしない。2025年の行（1692行）では、合算する17列のどれにも空欄はなかった
- PA：Lahman には PA の列がないため、`AB + BB + HBP + SF + SH` で計算する。公式の打席数には捕手の打撃妨害による出塁なども含まれるため、計算した値と一致しないことがある。その影響の大きさは**未確認**（既存の検証済みプリセット2件では一致した。下記）
- 対象：計算した PA が 200 以上の選手（投手の打席も記録に含まれるため、打席の少ない選手を除く）。PA 200 以上の選手に投手が含まれるかは**未確認**（今回使った3つの CSV には守備位置の情報がなく、判別できない。判別には `Appearances.csv`・`Pitching.csv` などが必要）
- 所属球団：stint の番号が最も大きい行の `teamID` を最終所属とし、移籍した選手もシーズン合計を最終所属の球団に置く。在籍した球団の一覧（stint の順。続けて同じ球団が並ぶ場合は1つにまとめ、元の球団に戻った場合はもう一度並べる）も集計する。readme の BATTING TABLE には「stint          player's stint (order of appearances within a season)」と書かれている（原文のまま）
- 球団コード：`teamID` は Lahman 独自のコードで、一般的な略号と異なるものがある（2025年の例：New York Yankees は `NYA`、San Diego Padres は `SDN`、Los Angeles Dodgers は `LAN`、Chicago White Sox は `CHA`。`Teams.csv` の `teamIDBR` 列では、それぞれ `NYY`・`SDP`・`LAD`・`CHW`）。2025年の `Teams.csv` には30球団がある
- 名前は `People.csv` の `nameFirst`・`nameLast`、球団名は `Teams.csv` の `name` を使う（接尾辞は下の「名前の接尾辞」の上書きで足す）
- API と同じ入力検証（2-1）を各選手に適用し、違反した選手を一覧にする

- 受け付けるのは、`People.csv` の名前の後ろに、半角スペースと半角 ASCII の接尾辞（`Jr.`・`Sr.`・`II`・`III`・`IV`）を足すことだけ。接尾辞より前の部分が元の名前と1文字でも違えば、スクリプトはエラーで止まる（アクセントつきの文字は元の表記のまま。例：Ronald Acuña Jr.）
- 生成（`--generate`）では、`People.csv` から作った名前に上書きを当てる。`--names-only` は元データを使わず、既存のプリセットの `name` の行だけを書き換える。`name` 以外の行・キーの順番・ファイル名が変わる場合や、ファイルが生成スクリプトの書き出しの形でない場合は、何も書かずに止まる。2回続けて実行しても結果は同じ。上書きにあってプリセットにない playerID は警告として一覧に出す。照合済みの2件（`aaron_judge_2025`・`luis_arraez_2025`）は対象外

- 13人の表記は、利用者が確認したものを手で入力した。`checked_source` は「ユーザー確認（確認元の詳細は記録なし）」で、確認元のサイト名などは記録していない
- 同じ名前の別の選手を区別する画面の仕組み（打順に同じ表示名があるとき「 (2)」を付ける。`frontend/src/names.ts`）は、この上書きとは別のもので、そのまま働く。Max Muncy の2人（`muncyma01`・`muncyma02`）は上書きの対象ではない

## 3. 使用データソース

### 3-1. 打者成績

- **対象シーズン**：2025年MLBレギュラーシーズン（規定打席到達者）
- **取得元**：Baseball Savant と Baseball-Reference（両者の数値が一致することを照合。取得元URL・取得日は各プリセットJSONの `source` 欄に記載）
- 取得項目：PA, AB, H, 2B, 3B, HR, BB, HBP, SO, SF, SH, GIDP, SB, CS

### 3-2. wOBA・wRC+（参考値として公表値を表示する）

wOBA・wRC+ は、API でもフロントエンドでも計算していない。公式の wOBA は故意四球を除くが、このアプリの成績には故意四球がなく、wRC+ は球場補正を要するため、公表値を保存して表示する。

- 公表値は、プリセットのJSONの任意の欄 `reference_metrics` に書く。欄の内容は、wOBA・wRC+（少なくとも一方）、対象シーズン、出典（出典名と `https://` で始まるURL）、取得日、備考（任意）
- 書いてよいのは、出典で確認した公表値だけである。未確認の値や仮の値は書かない（書いてあること自体が、出典で確認済みという意味になる）。プリセットの `verified` は成績（`stats`）の確認状況を表す欄で、参考値の確認状況は表さない
- 対象シーズンは、プリセットの `season` と同じ年でなければならない（`backend/tests/test_preset_schema.py` で確認）
- **この値はモデルの計算には使わない**。画面には「参考値（モデルの計算には使っていません）」と、出典・シーズンを添えて表示する。`reference_metrics` が無いプリセット、手入力の打者、プリセットを読み込んだあとに成績を編集した打者には表示しない
- `GET /presets` は、書かれた値を計算も加工もせずにそのまま返す（無ければ `null`）

以前は、FanGraphs "Guts!" の2025年の係数を使って、アプリが wOBA と簡易版の wRC+（球場補正なし）を計算し、`GET /presets` の `summary` に入れていた。上の理由で、公表されている値と同じ定義では計算できないため、計算と係数を削除した。

### 3-3. 進塁確率（暫定パラメータ）

## 4. 出力設計

- 基本値として「1試合あたりの期待得点」をまず算出する（AもBもここが起点）。
- 「N試合換算」は `1試合あたりの期待得点 × N` の単純計算である。API は1回の実行で、143試合と162試合に換算した値（入力打順・最適打順）を `totals_by_games` として返す。画面では「143試合」「162試合」の2択を切り替えて表示する（既定は143試合）。画面側では計算せず、API が返した値を表示するだけなので、切り替えに再計算は要らない
  - 切り替わるのは試合数だけで、確率はMLBのデータ・文献値のままである（NPB向けのモデルではない）
  - 従来からあるリクエストの `n_games`（既定143、1〜200）と、それに対応するレスポンスの `*_runs_n_games` も残している
- 計算はできるが利用者に知らせるべき点（PA と内訳の合計の不一致など）は、レスポンスの `warnings`（文字列の配列）で返す。入力打順の評価と最適打順の探索は同じ `POST /lineup/evaluate` の1回の呼び出しで行うため、警告もこのレスポンスにまとめて入る
- 「非効率%」：`(最適打順の期待得点 − 入力した打順の期待得点) ÷ 最適打順の期待得点 × 100` で算出し、「推奨打順を100%とした場合、あなたの打順は◯%の効率です」のように表示する（画面では、探索で求めた打順を「推奨打順」と呼ぶ）。
- 損失点（推奨打順に対して、入力打順で少なくなる得点）も API が計算して返す。画面ではこの値をそのまま出し、フロントで引き算をしない
  - `runs_lost_per_game`：1試合あたり。`best_order_runs_per_game − input_order_runs_per_game`
  - `totals_by_games[].runs_lost`：試合数ごと。同じ要素の `best_order_runs − input_order_runs`
  - 推奨打順の探索は入力打順から始め、それより期待得点が高い打順だけを採るため、0 以上になる。入力打順が推奨打順と同じなら 0

**結果の画面**（`frontend/src/components/ResultSummary.tsx`）

- 上から順に、試合数の切替、非効率%と損失点、2つの打順の一覧を出す。一覧は「入力打順」と「推奨打順（近似探索）」を、画面の幅にかかわらず左右に並べる（HTML の順番でも、入力打順が先）
  - 各行は固定の構造にして、どの打者でも同じ高さにする。1行目は「番号・表示名・（狭い列の札は名前のすぐ後ろ、広い列の札は行の右端）」で、折り返さない。札は縮めず切らず、収まらないときは名前の側を「…」で省略する。2行目以降は指標の固定の格子。文字は 12.8px（0.8rem）以上で、横スクロールが出ないようにする（幅 320・360・400・480・600・800・1200px で確認）
  - 名前・札・指標の切り替えは、画面の幅ではなく列の幅で決める（CSS の container query）。container は各行（`li`）にする（列の `section` を container にすると、レイアウトの封じ込めで `subgrid` が効かなくなるため。`li` の幅は列の内側の幅と同じ）。切り替えの幅は Edge 155 で実測して決めた
    - 列の幅 255px 以上：フルネームと「9番→1番」の札。それ未満は短い名前と「元9番」の札。根拠：「9番 Pete Crow-Armstrong 9番→1番」の1行目の幅が 254.5px
    - 列の幅 200px 以上：指標6つ（AVG・OBP・SLG・OPS・HR・SB）を3列×2段。それ未満は OBP・SLG を外し（`display: none` で、画面からも読み上げからも外す）、AVG → OPS → HR → SB の4つを2列×2段。根拠：最も広い指標（AVG .306）が 53.8px で、3列と間隔 8px×2 で 177.4px。OPS が 1 以上で1桁多くなる分を見込んで 200px にした
    - 列の幅 344px 以上：指標6つを6列×1段。根拠：指標の幅の合計と間隔 12px×5 で 335.4px。同じく1桁多くなる分を見込んだ
    - 文字の幅はフォントによって変わる（実測は Windows の Edge）。container query が使えないブラウザでは、狭い列の表示（短い名前・「元9番」・指標4つ）になる
  - 幅 800px 未満では、一覧の上の期待得点（1試合あたり・合計）を縦に並べ、枠の内側の余白と列の間隔を小さくする
  - 2つの一覧の同じ番号の行は、同じ高さ・同じ位置にそろえる。行の構造の固定で高さはそろうが、安全のため、外側を12行（見出し・期待得点・9人・シミュレーションの欄）の CSS グリッドにし、各列（`section`）と各一覧（`ol`）を `subgrid` にして行も共有する（見出しが片側だけ2行に折り返したときも、行の位置がそろう）。HTML の構造（`section > h4・dl・ol > li`）と順番（入力打順が先）、キーボードの移動順、読み上げの順番、aria の属性は変えない
  - `subgrid` が使えないブラウザでは、`@supports` の中の指定が無視され、各列が独立して縦に並ぶ。行の高さは同じままだが、狭い画面で「推奨打順（近似探索）」の見出しが2行になると、推奨打順の側が全体に1行分（実測 27px）下がる
  - 狭い列（列の幅 255px 未満）では、表示名を短くする（表示だけの整形で、表示名のデータは変えない。`frontend/src/format.ts` の `shortDisplayName`）。最初の単語をイニシャルにする（例：Aaron Judge → A. Judge、Ronald Acuña Jr. → R. Acuña Jr.、Max Muncy (2) → M. Muncy (2)）。対象は、空白で区切られた2語以上で、最初の単語がラテン文字（アクセントつきを含む）で始まり、残りに接尾辞（Jr.・Sr.・II・III・IV）以外の文字を含む単語がある名前だけ（Fernando Tatis Jr. → F. Tatis Jr.、Michael Harris II → M. Harris II）。1語の名前、日本語の名前、最初の単語が既にイニシャル（J.D. など）の名前、残りが接尾辞だけの名前（Tatis Jr. など）はそのまま。見た目の名前（フルネームと短い名前）は `aria-hidden` にし、フルネームを `title` と読み上げ用の文字で1回だけ伝える
- 試合数の切替は「143試合」「162試合」のラジオボタン（キーボードの矢印でも切り替わる）。近くに「試合数のみの切替で、確率はMLBデータ・文献値のままです」と注記する。選択肢は API の `totals_by_games` の `n_games` から作り、選んだ試合数の合計は `totals_by_games` の値をそのまま出す（フロントで掛け算をしない）。選んだ試合数は、計算し直しても保つ
- 非効率% は、2つの一覧の下ではなく、上の目立つ位置に大きく出す（API の `inefficiency_percent`）。その下に「入力打順だと、推奨打順より、1試合あたり ○ 点・選んだ試合数で ○ 点少なくなります」と損失点を出す（`runs_lost_per_game` と、選んだ試合数の `totals_by_games[].runs_lost`。試合数の切替に連動する）。損失点が 0 のときは「入力打順と推奨打順の期待得点は同じです」と出す
- 各打順の一覧の上に、1試合あたりの期待得点（`*_runs_per_game`）と、選んだ試合数の合計を出す
- 各行は、打順の番号・表示名と、少なめの指標（AVG・OBP・SLG・OPS・HR・SB。狭い列では AVG・OPS・HR・SB の4つ。`POST /batters/metrics` の値。画面は略号、読み上げは日本語の名前）
- 推奨打順の各行には、入力打順から動いたことを示す札を付ける。広い列は行の右端に「3番→1番」、狭い列は名前のすぐ後ろに「元3番」と出し（例：「1番 A. Judge [元9番]」）、行を増やさない。札は枠線と薄い背景（`--color-badge-bg`）の小さな札で、色だけに頼らず文字と枠で伝える（文字・枠・背景のコントラストは `npm run contrast` で確認）。どちらも見た目だけ（`aria-hidden`）で、読み上げは幅によらず「入力打順の3番から1番へ」の1文。動かなかった打者は、見た目には何も出さず、読み上げ用の文字で「変更なし」と伝える。印は、API が返す2つの打順（`input_order` と `best_order`。打者 ID の並び）の位置を比べるだけで、新しい値は作らない
- 入力打順の一覧の下に、たたんだ「参考：シミュレーション」の欄を置く（初期は閉じる。開閉ボタンは `aria-expanded` で状態を伝える）
  - 出すのは、API の `monte_carlo` の `mean`（平均）・`std`（標準偏差）・`n_trials`（試合数）だけで、「5000試合の1試合あたりの得点：平均 ○、標準偏差 ○」の形にする。最小・最大は、極端な1試合が目立って誤解を招くおそれがあるため出さない
  - 乱数を使うため計算のたびに少し変わること、上の期待得点（案A、厳密な計算）とほぼ一致するかを確かめる参考値であることを注記する。API は入力打順だけを案Bで評価するため、推奨打順の分は出さない（欄の中でもその旨を書く）
- 打席数が少ない打者の一覧（「計算と結果」の上）と、計算したあとに入力・打順を変えたときの案内は、段階7の表示のまま

### 打者ごとの表示用の指標（`POST /batters/metrics`）

画面で打順を並べ替えるときの参考として、打者ごとの指標を返す。得点期待値の計算は行わない。画面に出す数値は API が返した値だけにする方針のため、フロントエンドでは計算せず、このエンドポイントで計算する。

- 入力：1〜9人分の成績（`batters`。検証ルールは 2-1 と同じ）と、任意の `display_names`
- 出力：打者 ID ごとに、次の指標と、その打者についての注意
  - `warning_items`：種類つきの注意 `[{"code": 種類, "message": 文}]`。種類は `PA_SUM_MISMATCH`（打席数と、打数+四球+死球+犠飛+犠打の合計が合わない）と `LOW_PA`（打席数が `LOW_PA_THRESHOLD` 未満）の2つ。`PA_SUM_MISMATCH` は、入力検証の共通の例（`schemas/batter_stats_validation_cases.json`）とフロントの入力検証で使っている名前と同じ
  - `warnings`：以前からの互換のために残している欄。`warning_items` の `message` を同じ順に並べたもの（1回作った注意から両方を作るので、ずれない）。`POST /lineup/evaluate` が返す `warnings` と同じ文

| 指標 | 定義 |
|---|---|
| `PA`・`H`・`HR`・`SB`・`CS` | 入力値のまま |
| `AVG`（打率） | H ÷ AB |
| `OBP`（出塁率） | (H + BB + HBP) ÷ (AB + BB + HBP + SF) |
| `SLG`（長打率） | 総塁打 ÷ AB（総塁打 = 単打 + 2×二塁打 + 3×三塁打 + 4×本塁打） |
| `OPS` | 出塁率 + 長打率 |
| `BB_pct`（四球率） | BB ÷ PA |
| `SO_pct`（三振率） | SO ÷ PA |

- 分母が 0 で計算できない指標は `null` を返す（計算できて 0 になる場合と区別するため）。画面では「—」と表示する。OPS は、出塁率か長打率のどちらかが `null` なら `null`
- 率は丸めずに返す。桁をそろえるのは表示する側で行う
- wOBA・wRC+ は返さない。このアプリでは計算しない（3-2）

## 5. 検証方法

1. **確率の整合性チェック**：各状態からの遷移確率の合計が1になっているかのユニットテスト
2. **単調性チェック**：本塁打確率を上げてアウト確率を下げたら得点期待値が必ず上がるか、といった論理的妥当性のテスト
3. **A・B同士の突き合わせ**：同一入力・同一進塁ルールでAとBを計算し、Bの試行回数を増やしたときにAの値へ収束するか確認
4. **既知の実測値とのベンチマーク**：
   - 平均的なMLB打者9人の1試合期待得点が、実際のMLB平均得点（近年4.3〜4.7点/試合程度）に近いか
   - 実在チームの実成績を入力し、143試合・162試合換算した値が実際のシーズン総得点と近い範囲に収まるか（多少のズレは許容）
5. **先行研究との照合**：Bukietら、D'Esopo and Lefkowitzらの論文に載っている計算例を同条件で再現し、近い結果が出るか確認

READMEには④⑤の具体的な検証結果を実装後に数値・グラフ付きで記載する。

## 6. README：考慮していない点・モデルの限界

### NPBとMLBの環境差全般
本モデルはMLBデータで構築しているため、NPB選手やNPBの試合環境にそのまま適用すると精度が落ちる可能性がある。

- 使用球の違い（反発係数の違いによる長打の出やすさの差）
- 球場サイズ・パークファクターの違い
- リーグルールの違い（NPBはセ・リーグDH無し、パ・リーグDH有り／MLBは両リーグDH）
- 試合数の違い（MLB162試合／NPB143試合）に伴う疲労・故障リスク等は未モデル化
- 延長戦ルールの違い（NPBのタイブレーク・引き分け制度）は未考慮

### モデル全般の限界

- 相手投手の影響（左右・調子・対戦成績によるプラットーン効果）は未反映。全打席を平均的な対戦環境として扱う（シーズン換算のため平均的には均されると考えられる）
- 守備・守備位置・シフトは考慮しない
- 走塁は盗塁（一塁→二塁）のみモデル化。三盗・本盗は対象外
- 走者の進塁能力は打者個人差を反映せず、リーグ平均の進塁確率（2003年データ）を暫定使用。打者本体データ（2025年）と年代が異なる
- 打球アウトによる進塁・生還の一部が未対応（内野ゴロでの生還、0/1アウト時のフライでのタッチアップ進塁など）
- 相手の守備範囲・エラーは考慮しない
- 敬遠は通常の四球と区別しない
- 犠打は成功パターンのみモデル化（失敗・セーフティバント・スクイズ特有の分岐は考慮しない）
- 打順は固定とし、シーズン中の交代・怪我・打順変更は考慮しない
- 各打席のイベント確率は独立同分布と仮定（調子の波・クラッチ度等は未反映）
- 采配（バント・敬遠・代打・盗塁タイミングの判断等）は考慮せず、機械的に確率を適用
- シーズンを通して確率が一定と仮定（シーズン内変動・年齢による衰え等は反映しない）
- パークファクターによる補正は行っていない
- 打席数が少ない打者も、入力された成績をそのまま確率に使う（標本が小さいことによる不確かさの補正や、平均への回帰は行わない）。PA が 200 未満の打者には注意を出すが、200 は本プロジェクトの目安で、出典・統計的根拠はない（2-1）

### 指標に関する補足

Statcastのx系指標（xBA, xwOBA等）は「運を除いた実力評価」を目的とした指標であり、実際の結果とあえて乖離するよう設計されているため、本モデルの入力には使用していない（本モデルは実際に起きた結果ベースのカウント統計を使用）。

## 9. アルゴリズム詳細（擬似コード）

### 状態のインデックス化

```
0-23: (走者状況, アウト数) の組み合わせ
  idx = 走者状況コード(0-7) * 3 + アウト数(0-2)
24: 3アウト到達（イニング内の吸収状態）
```

### 打者ごとの1打席分遷移行列の構築（A・B共通）

```
function build_batter_transition(event_probs, advance_probs):
    T = 25x25 のゼロ行列  # 状態遷移確率
    R = 25x25 のゼロ行列  # その遷移で入る得点数
    for each state (runners, outs) in 0..23:
        for each event in event_probs:
            new_runners, new_outs, runs_scored = resolve_event(
                event, runners, outs, advance_probs[outs]
            )
            T[state][new_state] += event_probs[event] * branch_prob
            R[state][new_state] = runs_scored
    return T, R
```

盗塁は`(S1, *)`・`(S13, *)`状態限定で、打者の遷移を適用する前に別途「企図→成功/失敗」の遷移を挟む。案Aでは盗塁ステップの遷移行列 S（`transitions.build_steal_transition`）を打者の遷移行列 T の前に合成する（`S × T`）。

### 案A：マルコフ連鎖による厳密計算

複合状態 `(base_out_state, batter_index, inning)` を定義し、9回終了(3アウト到達)で「試合終了」に吸収させる。

```
function build_game_transition(batter_matrices):  # batter_matrices[1..9]
    複合状態空間を構築 (base_out ∈ 0..24, batter_index ∈ 1..9, inning ∈ 1..9)
    for each 複合状態 (s, i, n):
        if s == 24 (3アウト到達):
            if n == 9: 「試合終了」へ吸収
            else: (S0/0アウト, i, n+1) へ遷移（打順iは継続）
        else:
            batter_matrices[i].T に従って次のbase_out_state s'へ遷移
            次の複合状態は (s', i+1 mod 9, n)
            reward(得点)を記録

    基本行列 N = (I - Q)^(-1) を計算
    期待総得点 = N × reward_vector（初期状態: S0/0アウト, 1番打者, 1回）
    return 期待得点(1試合)
```

行列演算のみで完結するため、9!=362,880通りの全打順探索と相性が良い。

### 案B：モンテカルロシミュレーション

```
function simulate_one_game(batter_event_probs_list, advance_probs, steal_probs):
    state = (S0, 0アウト), inning=1, batter_idx=1, runs=0
    while inning <= 9:
        if 一塁に走者がいて二塁が空いている状況:
            一塁走者本人の盗塁企図/成功を乱数で判定し状態更新
        event = 現在の打者の確率分布から乱数サンプリング
        new_state, runs_scored = resolve_event(event, state, advance_probs)
        runs += runs_scored
        state = new_state
        batter_idx = (batter_idx % 9) + 1
        if state == 3アウト到達:
            inning += 1
            state = (S0, 0アウト)
    return runs

function estimate_season_runs(batter_list, N_trials=100000):
    total = sum(simulate_one_game(...) for _ in range(N_trials))
    return total / N_trials  # 1試合あたりの期待得点
```

### 使い分けの推奨（計算量からの示唆）

- 全打順探索（9!通り）による最適打順探索 → **案A**（行列演算で一瞬）。案Bで362,880通り×数万試行は非現実的。
- 入力した1打順の確率的なブレ幅（最良/最悪ケース）の提示 → **案B**。
- 推奨：最適打順探索は案Aで実施し、入力打順については案Aの厳密値に加え案Bのシミュレーション分布も参考表示する。

### 最適打順探索の実運用方式（決定事項）

実装・実測の結果、以下が判明した。

- 全探索(362,880通り)は、現行コードで**約8.5分（512.1秒）**かかる（実測。計測条件は下記「計算速度の改善」節）。APIの同期レスポンスとしてはまだ重すぎる。
- 山登り法（2人入れ替えの近傍探索）は1回あたり数十msで完了するが、**1回だけの試行だと局所最適解に留まり、真の最適解を逃すリスクがある**。
- そこで、**複数回のランダム再スタートによる山登り法**を採用し、試行回数は固定ではなく**適応的停止**で決める：
  - 最低 `min_restarts=10` 回は必ず試行する
  - 連続 `patience=10` 回、最良値が更新されなければ打ち切る
  - 最大でも `max_restarts=50` 回で打ち切る（上限キャップ）
  - 1回目の試行はユーザーが入力した打順から、2回目以降はランダムな初期打順から開始する

  この方式により、`p`（1回の山登り法で最適解圏に到達する確率）が未知でも、試行回数を過不足なく動的に調整できる。固定回数を決め打ちするより無駄が少ない。
- 実装は `backend/app/core/optimizer.py` の `multi_restart_hill_climb` を参照。APIのデフォルトはこちらを使用する。
- 厳密な全探索用の関数（`find_optimal_lineup`）も別途実装済みで、バックグラウンドジョブ等での利用を想定している。

### 計算速度の改善（遷移行列のキャッシュ・OpenBLASのスレッド数）

以前の版の本書・READMEでは全探索の所要時間を「約20.5分（キャッシュあり）」と記載していたが、計測条件は不明で、当時のコードには遷移行列のキャッシュは実装されていなかった。本節の改善後に現行コードで測り直した値は次のとおり。

- **全探索（`find_optimal_lineup`、362,880通り）：512.1秒（約8.5分）**
- 計測条件：Intel Core Ultra 7 265（論理CPU 20）・Windows 11・Python 3.13.14・numpy 2.4.4、`OPENBLAS_NUM_THREADS=1`（既定値）、遷移行列のキャッシュあり（打者9件・盗塁2件を構築し、以降はすべて再利用）。打者は `tests/test_optimizer.py` と同じ多様な9人、盗塁確率はプリセット2名（Judge/Arraez）の値を交互に設定（APIと同じく盗塁あり）。1回のみの計測

1. **遷移行列のキャッシュ**：`transitions.build_batter_transition`（既定の進塁確率のときのみ）と `build_steal_transition` の結果を `functools.lru_cache`（上限1024件）で再利用する。キーはイベントの並び順も含めた（イベント, 確率）の組で、毎回構築した場合と同一の値になる。共有する配列は読み取り専用にしている
2. **OpenBLASのスレッド数の既定値を1にする**：案Aは216×216の小さな行列の逆行列計算を大量に繰り返すため、OpenBLASのマルチスレッド化がかえって遅くなっていた（216×216の逆行列1回：既定のスレッド数で50.75ms、1スレッドで0.61ms）。`backend/app/__init__.py` で numpy の読み込み前に `OPENBLAS_NUM_THREADS` の既定値を1にする
   - 利用者が環境変数 `OPENBLAS_NUM_THREADS` を設定している場合はそちらが優先される（`os.environ.setdefault`）
   - numpy が app より先に読み込まれると効かない。テストでは `tests/conftest.py` で app を先に読み込む
   - OpenBLAS向けの設定であり、Accelerate など別のBLASを使う環境で効くかは未確認
   - pytest 実行中（全テスト・単独ファイル）と `uvicorn app.main:app` で起動したプロセスで、BLASのスレッド数が1になっていることを threadpoolctl で確認した（`--reload` 付きの起動は未確認）

**実測結果**（Windows 11・論理CPU 20・Python 3.13.14・numpy 2.4.4・OpenBLAS 0.3.31。`POST /lineup/evaluate` は Judge/Arraez を交互に並べた9人で3回計測）

| 構成 | テスト全体（24件） | `POST /lineup/evaluate` |
|---|---|---|
| 改善前 | 194.1秒 | 29.0秒 / 18.5秒 / 27.1秒 |
| キャッシュのみ | 54.8秒 | 14.1秒 / 13.2秒 / 11.0秒 |
| キャッシュ＋スレッド数1 | 13.4秒 | 1.84秒 / 1.88秒 / 1.90秒 |

計算結果への影響：固定の打順16パターン（盗塁なし・あり）の案Aの期待得点は、改善前との差が最大 1.8e-15（キャッシュのみでは差0）。seed を固定した案Bの結果は完全に一致した。

## 10. プリセットデータのJSON Schema

スキーマの実体は [`schemas/batter_preset.schema.json`](../schemas/batter_preset.schema.json) を参照（二重管理を避けるため、本書には転載しない）。全プリセットがこのスキーマに合うことは `backend/tests/test_preset_schema.py` とCI（`preset-validation`）で検証している。

打率・出塁率・長打率などの表示用指標はこのJSONには含めず、アプリ側が`stats`から計算する（`GET /presets` のレスポンス時に `summary` として付与）。wOBA・wRC+ はアプリでは計算せず、公表値を任意の `reference_metrics` 欄に書いた場合だけ表示する（3-2）。管理者はこのSchemaに沿ったJSONファイルを`data/presets/mlb/2025/`に追加するだけで新規選手を追加できる。

スキーマの決まり：

- 一番上の階層と `reference_metrics` は、スキーマにないキーを受け付けない（キーの書き間違いが、無視されずにエラーになるようにするため）
- `stats.PA` は 1 以上（API の検証と同じ）
- 任意の `team_info`（球団コード・球団名・リーグ・地区（`division`、E・C・W のいずれか、省略可））と `teams_played`（複数の球団に在籍した選手だけ。2件以上、出場した順）がある。`teams_played` があるときは `team_info` も必要で、`teams_played` の最後の球団は `team_info.code` と同じでなければならない（スキーマでは書けないため `check_preset` で検査）
- `source` には任意の `note`（生成の方法や照合の状況などの補足）を書ける
- `source.url` と `reference_metrics.source.url` は、`https://` で始まるURLだけを受け付ける（画面でリンクにするため）
