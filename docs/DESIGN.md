# 打順シミュレーター 設計

この文書は、打順シミュレーターの計算方式、入力と出力、データの作り方、画面の設計をまとめたものです。使い方と起動のしかたは [`README.md`](../README.md)、検証の結果と測定値は [`VALIDATION.md`](VALIDATION.md) を参照してください。

## 1. 概要と用語

この章では、アプリが何を計算するかと、この文書で使う言葉を説明します。

MLBの打撃成績（回数で数えた成績）から、9人の打順の1試合あたりの期待得点を計算し、次の3つを示します。

1. 入力打順（画面で並べた打順）の期待得点
2. 推奨打順（打順の探索で求めた、期待得点が高くなる打順）とその期待得点
3. 2つの差（非効率% と、1試合あたり・試合数あたりの損失点）

推奨打順は近似の探索で求めるため、最も期待得点が高い打順とは限りません（4章）。

| 用語 | 意味 |
|---|---|
| 選手データ | あらかじめ用意した、選手の打撃成績。コード・API・ファイル名では preset と呼ぶ（`data/presets/`、`GET /presets`、`schemas/batter_preset.schema.json` など）。この文書では、文章では「選手データ」、コードや API の名前は preset のまま書く |
| 入力打順 | 画面で並べた打順。API の `input_order` |
| 推奨打順 | 探索で求めた打順。API の `best_order` |
| 案A | マルコフ連鎖（吸収連鎖）による厳密計算（3章） |
| 案B | モンテカルロシミュレーション（3章） |
| 打者 ID | 打者を区別するための内部の値（画面では `b1`〜`b9`）。画面には出さない |
| 表示名 | 画面に出す打者の名前（既定は「打者A」〜「打者I」） |

## 2. 全体の構成

この章では、どの部分が何を受け持つかと、計算の流れを示します。

- **バックエンド**（`backend/`、Python 3.12 以上、FastAPI）
  - `app/main.py`：API の入口
  - `app/schemas/batter.py`：入力の型と検証の規則、注意の文
  - `app/core/states.py`：状態空間（3章）
  - `app/core/transitions.py`：打撃イベントごとの遷移ルールと、打者1人分の遷移行列（案A・案Bで共通）
  - `app/core/markov.py`：案A
  - `app/core/monte_carlo.py`：案B
  - `app/core/optimizer.py`：推奨打順の探索（4章）
  - `app/core/metrics.py`：表示用の指標と、イベント確率・盗塁の確率の算出
  - `app/data_loader.py`：選手データの読み込み
  - `app/web.py`：公開用の配信アプリ（API を `/api` の下に載せ、ビルドしたフロントエンドも配信する。下の「デプロイの構成」）
- **フロントエンド**（`frontend/`、React + TypeScript + Vite）
  - `src/App.tsx` と `src/components/`：画面（8章）
  - `src/api/client.ts`：API の呼び出し。画面は API を相対パス `/api/...` で呼び、開発サーバーが `/api` をバックエンド（`http://127.0.0.1:8000`）に転送する（`vite.config.ts`）
  - `src/state/lineup.ts`：9人分の入力の状態
  - `src/validation.ts`：入力の検証（バックエンドと同じ規則。5章）
- **データ**：`data/presets/mlb/2025/`（選手データ、1人1ファイル）、`data/overrides/display_names.json`（選手名の接尾辞）、`data/NOTICE`（出典とライセンス）
- **スキーマ**：`schemas/`（選手データの JSON Schema と、バックエンドとフロントエンドで共通に使う入力検証の例）
- **生成スクリプト**：`scripts/build_lahman_presets.py`（7章）

計算の流れ（`POST /lineup/evaluate`）：

1. 9人分の成績を検証し、打者ごとにイベント確率（11種類）と盗塁の確率を求める
2. 入力打順の期待得点を、案Aで計算する
3. 推奨打順を、案Aを繰り返し呼ぶ多点の山登り法で探す（4章）
4. 入力打順を、案B（試行回数は既定 5000。環境変数 `MONTE_CARLO_TRIALS` で変えられる。3-6）でも評価し、得点の分布を参考値として添える
5. 期待得点、試合数ごとの合計、非効率%、損失点、注意の文を返す

画面に出す数値は、API が返した値だけです。フロントエンドでは、確率・期待得点・指標を計算せず、桁をそろえるなどの表示の整形だけを行います。

### デプロイの構成

公開用には、1つの Web サービスとして動かします。FastAPI が、API とビルドしたフロントエンドの両方を配信します。

- **配信用のアプリ**（`backend/app/web.py`、起動は `uvicorn app.web:app`）：今の API（`app.main` の app）は変えずに `/api` の下に載せる。パスは、開発時の Vite の中継（`/api` を取り除いて転送）と同じになる（例：`/api/lineup/evaluate`）。API の自動ドキュメントは `/api/docs`。それ以外のパスは `frontend/dist` のファイルを返し、存在しないパスには `index.html` を返す。`/api` の下の存在しないパスは 404 のまま。ビルド出力（`index.html`）が無いときは、`app.main` の app をそのまま使う（開発時は今までどおり `uvicorn app.main:app` と Vite の開発サーバーを使う）
- **イメージ**（リポジトリの直下の `Dockerfile`）：2段階で作る。1段目は `node:24.19.0-bookworm-slim` で `npm ci` と `npm run build`、2段目は `python:3.13.14-slim-bookworm` で、実行時の依存だけを入れる（開発用の `[dev]` は入れない）。リポジトリと同じ並び（`backend`・`data/presets`・`frontend/dist`）に置き、選手データの場所がソースの位置から決まるため、`app` はソースのまま動かす。root ではないユーザーで動かす。ヘルスチェックは `/api/health`。イメージに入れないものは `.dockerignore` に書く
- **環境変数**：`PORT`（待ち受けるポート。既定 8000）、`FRONTEND_DIST_DIR`（ビルド出力の場所。既定はリポジトリの `frontend/dist`）、`MONTE_CARLO_TRIALS`（案Bの試行回数。アプリの既定は 5000。イメージでは 1000 にしている。3-6）。`OPENBLAS_NUM_THREADS` の既定値（1）は、今までどおり `app/__init__.py` が設定する（4-2）。秘密情報は使わない
- **無料の枠で想定される制約**：使われない時間が続くとサービスが止まり、次のアクセスで再開するまでに時間がかかる（Render の説明では、15分間アクセスが無いと停止し、再開に約1分かかる。この公開先での再開の時間は未確認）。CPU が小さいため、計算は手元の PC よりかなり遅い。そのため、案A の評価と推奨打順の探索を速くし（4-2）、イメージでは案Bの試行回数を 1000 にしている（推奨打順と期待得点は変わらず、参考のシミュレーションの値のぶれが大きくなる）。公開先での計算の時間は、VALIDATION.md 8章を参照
- 確かめたこと：公開先（Render の無料の Web サービス、Docker）で、イメージのビルドが通り、起動し、画面から計算できた（選手データ9人で約12秒。VALIDATION.md 8-3）。手元では docker を使っておらず、同じ並びと実行時だけの依存で `uvicorn app.web:app` を起動し、画面が開き、計算が動くことを確かめた
- 未確認のこと：停止したあと、次のアクセスで再開するまでの時間（Render の説明では約1分）。Linux 上での HEALTHCHECK の動き

## 3. 計算モデル

この章では、得点期待値を計算するモデル（状態、遷移ルール、盗塁）と、2つの計算方式（案A・案B）を説明します。2つの方式は、同じ遷移ルール（`transitions.resolve_event`）を使います。

### 3-1. 状態空間

走者状況（8通り）× アウト数（0・1・2）＝ 24状態に、3アウト（イニングの終わり）を加えた、25状態です。

| 走者状況 | 意味 | コード |
|---|---|---|
| S0 | 走者なし | 0 |
| S1 | 一塁のみ | 1 |
| S2 | 二塁のみ | 2 |
| S3 | 三塁のみ | 4 |
| S12 | 一・二塁 | 3 |
| S13 | 一・三塁 | 5 |
| S23 | 二・三塁 | 6 |
| S123 | 満塁 | 7 |

走者状況は3ビット（一塁＝1、二塁＝2、三塁＝4）のコード（0〜7）で表し、状態の番号は `走者状況のコード × 3 + アウト数`（0〜23）、24 を3アウトとします（`app/core/states.py`）。

### 3-2. イベント確率

入力された成績（回数）から、11種類のイベント（四球 BB、死球 HBP、単打 1B、二塁打 2B、三塁打 3B、本塁打 HR、三振 SO、そのほかの凡退 OUT、犠飛 SF、犠打 SH、併殺打 GIDP）の確率を求めます（`metrics.event_probabilities`）。

- 単打 ＝ 安打 − 二塁打 − 三塁打 − 本塁打
- そのほかの凡退 ＝ 打数 − 安打 − 三振 − 併殺打（負になるときは 0）
- 各イベントの数 ÷ 打席数（PA）を求め、合計が1になるように正規化する
- 打席数は入力の値をそのまま使います。打席数を内訳から自動で計算する方式は採りません。入力フォームで打席数を必須にする方針とそろえるためと、打席数と成績がすべて 0 の入力でサーバーエラーになったためです

### 3-3. イベントごとの遷移ルール

| イベント | 遷移 |
|---|---|
| 四球・死球 | 打者は一塁へ。押し出される走者だけが1つ進む |
| 単打 | 打者は一塁へ。三塁走者は生還。二塁走者は「生還」か「三塁で止まる」、一塁走者は「三塁まで進む」か「二塁で止まる」を、アウト数別の確率で分ける。後ろの走者は、前の走者の塁を超えず、同じ塁にも重ならない：二塁走者が三塁で止まったときは、一塁走者は二塁まで（一・二塁と満塁のとき）。二塁走者が生還したときは、一塁走者は独立に三塁まで進める |
| 二塁打 | 打者は二塁へ。二塁・三塁の走者は生還。一塁走者は「生還」か「三塁で止まる」を、アウト数別の確率で分ける |
| 三塁打 | 走者は全員生還し、打者は三塁へ |
| 本塁打 | 走者と打者が全員生還 |
| 三振 | 走者は動かず、アウトが1つ増える |
| そのほかの凡退 | 走者は動かず、アウトが1つ増える（打球アウトでの進塁・生還は扱わない。10章） |
| 併殺打 | 一塁に走者がいるとき、打者と一塁走者がアウト（アウトが2つ増える）。ほかの走者は動かない。一塁に走者がいなければ、通常の凡退として扱う |
| 犠飛 | 三塁に走者がいるとき、打者はアウトで、三塁走者が生還。三塁に走者がいなければ、通常の凡退として扱う |
| 犠打 | 打者はアウトで、走者は全員1つずつ進む（成功する場合だけを扱う）。三塁走者は生還し、三塁を空ける |

どの遷移でも、（遷移前の走者の数 ＋ 打者）＝（遷移後の走者の数 ＋ 得点 ＋ 増えたアウトの数）が成り立ち、2人の走者が同じ塁に置かれることはありません。11種類のイベント × 24状態のすべての分岐で、テスト（`backend/tests/test_transition_rules.py`）が確かめています（VALIDATION.md 2章）。

進塁の確率は、アウト数で「2アウト未満」と「2アウト」の2つに分けて持ちます（2アウトでは走者が積極的に走るため）。値と出典は 7-6 にあります。

### 3-4. 盗塁

一塁に走者がいて二塁が空いている状態（S1 と S13）でだけ、打者の打席の**前**に、盗塁の段を1つ挟みます（`transitions.apply_steal_step`）。一・二塁（S12）など、二塁が埋まっている状態の重盗は扱いません。

1. 一塁走者の盗塁企図率で、「企図する」か「しない」かを分ける
2. 企図した場合は、その走者の盗塁の成否で、「二塁へ進む（アウト数は変わらない）」か「盗塁死（アウトが1つ増える）」かを分ける
3. 盗塁死で3アウトになった場合、打席の打者は打席を終えていないので、次のイニングはその打者から始まる

**一塁走者の決め方（案Aと案Bで違う）**

- 案A：状態に走者の個人を持たないため、打者 k の打席の前の一塁走者を「直前の打者 k−1」とみなし、その打者の盗塁の確率を使う近似を行う。一塁走者が2〜3人前の打者である場合（後の打者が走者を動かさずにアウトになった場合など）に、誤差が生じる
- 案B：一塁に出た打者（四球・死球・単打）を追跡し、走者本人の盗塁の確率を使う

9人の盗塁の確率が同じなら、2つの方式は一致します。違う場合の差は、VALIDATION.md 3-2 を参照してください。

**盗塁企図率と盗塁死率の算出**（`metrics.steal_probabilities`）

- 企図率 ＝ (SB + CS) ÷ (単打 + 四球 + 死球)。一塁に出た回数を盗塁の機会とみなす（1.0 を上限とする）
- 盗塁死率（企図あたり）＝ CS ÷ (SB + CS)

企図率は「一塁に出た回数あたり」の値ですが、モデルでは「一塁に走者がいる打席ごと」に当てはめるため、一塁にいるまま複数の打席を迎える場合は、企図の回数がやや多めになりえます。また、失策や野選で一塁に出た回数は、機会に含めていません。三盗・本盗は扱いません（10章）。

### 3-5. 案A：マルコフ連鎖による厳密計算

乱数を使わずに、1試合（9イニング）の期待得点を厳密に求めます（`app/core/markov.py`）。打順がイニングをまたいで続く（イニングごとに1番打者へ戻らない）ことを反映します。

1. 打者ごとに、1打席分の 25×25 の遷移行列 T と、状態ごとの期待得点のベクトル reward を作る（`transitions.build_batter_transition`）。盗塁を扱うときは、盗塁の段の遷移行列 S（`transitions.build_steal_transition`）を打者の遷移の前に合成する（S × T）
2. （状態 0〜23、打者 1〜9）の 216 状態からなる「1イニング分」の吸収マルコフ連鎖を組み、基本行列 N ＝ (I − Q)⁻¹ から次の2つを求める。使うのは N のうち、各打者が先頭の状態の9行だけなので、逆行列全体は求めず、(I − Q)ᵀ x ＝ e（9本の右辺）の線形方程式で、その9行だけを解く
   - V[k]：打者 k が先頭（走者なし・0アウト）のときの、そのイニングの期待得点
   - M[k][j]：打者 k が先頭のとき、次のイニングの先頭が打者 j になる確率
3. 1回は1番打者から始め、先頭打者の分布を M で9イニング分進めながら、V を足し合わせる

```
function expected_runs_per_game(打者9人):
    for 打者 k in 1..9:
        T[k], reward[k] = build_batter_transition(打者 k のイベント確率)
        （盗塁あり）T[k] = S[k-1] × T[k]   # 一塁走者を直前の打者 k-1 とみなす

    # 1イニング分の連鎖（216状態 = 状態24 × 打者9）
    Q[(s, k) → (s', k+1)] = T[k][s → s']        # 3アウトにならない遷移
    R[(s, k) → 次の先頭 k+1] = T[k][s → 3アウト] # 3アウトで終わる遷移
    # N = (I - Q)^-1 のうち、走者なし・0アウトで各打者が先頭の9行だけを解く
    N_rows = solve((I - Q)^T, e_走者なし0アウト(各打者))^T
    V = N_rows × reward
    M = N_rows × R

    dist = [1, 0, ..., 0]   # 1回の先頭は1番打者
    total = 0
    for イニング in 1..9:
        total += dist · V
        dist = dist × M
    return total
```

盗塁死で3アウトになったときは、その打者が次のイニングの先頭になります（R に、盗塁の段の3アウトの確率を、同じ打者の欄へ足します）。行列の計算だけで終わるため、多くの打順を評価する探索（4章）に向いています。

### 3-6. 案B：モンテカルロシミュレーション

同じ遷移ルールを使い、乱数でイベントを1つずつ引きながら、試合を何回も繰り返して平均得点を求めます（`app/core/monte_carlo.py`）。得点の分布（平均・標準偏差・最小・最大）も求められます。

```
function simulate_one_game(打者9人, 盗塁の確率):
    打者 = 1番, 得点 = 0
    for イニング in 1..9:
        状態 = (走者なし, 0アウト), 一塁走者 = なし
        while アウト < 3:
            一塁走者本人の盗塁の確率で、盗塁の段を乱数で決める
            if アウト == 3: break
            イベント = 現在の打者のイベント確率から乱数で選ぶ
            分岐 = resolve_event(イベント, 状態) から確率で1つ選ぶ
            得点 += 分岐の得点; 状態 = 分岐の状態
            一塁走者を更新する（四球・死球・単打なら現在の打者）
            打者 = 次の打者
    return 得点

function estimate_expected_runs(打者9人, n_trials):
    n_trials 回 simulate_one_game を繰り返し、平均・標準偏差・最小・最大・n_trials を返す
```

- API（`POST /lineup/evaluate`）は、入力打順を、環境変数 `MONTE_CARLO_TRIALS` の回数（未設定なら 5000）だけ試行して評価する（`app/main.py`）。1 以上の整数でなければ、設定の誤りに気づけるよう、起動時にエラーにする。試行回数はレスポンスの `monte_carlo.n_trials` に入り、画面はこの値を表示する。公開用のイメージは、CPU が小さい無料の枠に合わせて 1000 にしている（推奨打順と期待得点（案A）は変わらない。参考の平均の標準誤差は、5000試行の約 0.046点から、1000試行で約 0.104点に大きくなる（Judge・Arraez を含む9人での手元の測定））。関数 `estimate_expected_runs` の試行回数の既定値は 20000（検証では 3万・20万試行。VALIDATION.md 3章）
- 試行回数を増やすと、案Aの厳密な値に近づくはずなので、案Aの検証に使う

### 3-7. 使い分けの推奨

- 推奨打順の探索 → **案A**。多くの打順を評価するため、行列の計算で速く求められる方式を使う。案Bで多くの打順を何万回も試行するのは、時間がかかりすぎる
- 入力打順の得点のばらつき → **案B**
- API は、入力打順と推奨打順の期待得点を案Aで求め、入力打順についてだけ、案Bの平均と標準偏差を参考値として添える（画面の「参考：シミュレーション」。8-5）

## 4. 推奨打順の探索と計算速度

この章では、推奨打順をどう探すかと、計算を速くするための工夫を説明します。測定値は VALIDATION.md 8章にあります。

### 4-1. 最適打順探索の実運用方式

- 9人の全打順（9! ＝ 362,880通り）を厳密に探索する関数（`find_optimal_lineup`）は、測定で約7.6分かかり（VALIDATION.md 8-1）、API の応答には長すぎる
- 2人を入れ替える近傍を探す山登り法（`hill_climb_lineup`）は速いが、1回だけでは局所的な最適解にとどまり、最も良い打順を逃すおそれがある
- そこで、**複数回のランダム再スタートによる山登り法**（`multi_restart_hill_climb`）を API の既定にした。試行の回数は固定せず、次の規則で止める
  - 最低 10回（`min_restarts`）は必ず試行する
  - 連続 10回（`patience`）、最良の値が更新されなければ止める
  - 最大でも 50回（`max_restarts`）で止める
  - 1回目は入力打順から、2回目以降はランダムな打順から始める
- 1回の山登りで最適解の近くに着ける確率が分からなくても、試行の回数を状況に応じて決められ、回数を決め打ちするより無駄が少ない
- 入力打順から始め、それより期待得点が高い打順だけを採るため、推奨打順の期待得点は入力打順以上になる
- 全探索の関数は、バックグラウンドでの処理などに使うことを想定して残している（API からは使っていない）

### 4-2. 計算速度の改善

1. **遷移行列のキャッシュ**：`transitions.build_batter_transition`（既定の進塁確率のときだけ）と `build_steal_transition` の結果を、`functools.lru_cache`（上限1024件）で使い回す。キーはイベントの並び順も含めた（イベント, 確率）の組で、毎回作った場合と同じ値になる。共有する配列は読み取り専用にしている
2. **OpenBLAS のスレッド数の既定値を1にする**：案Aは 216×216 の小さな行列の計算を何度も行うため、OpenBLAS のマルチスレッド化がかえって遅くなっていた。`backend/app/__init__.py` で、numpy を読み込む前に `OPENBLAS_NUM_THREADS` の既定値を1にする
   - 環境変数 `OPENBLAS_NUM_THREADS` が設定されていれば、そちらを優先する（`os.environ.setdefault`）
   - numpy が app より先に読み込まれると効かない。テストでは `tests/conftest.py` で app を先に読み込む
   - OpenBLAS 向けの設定で、Accelerate など別の BLAS を使う環境で効くかは未確認
3. **1イニングの連鎖を配列の操作で組み、必要な9行だけを解く**（`markov._half_inning_chain`）：216 状態の Q を、Python の二重ループではなく、打者ごとの 24×24 のブロックを配列の操作で置いて組む。N は、逆行列全体ではなく、各打者が先頭の状態の9行だけを線形方程式で解く（3-5）。元の形（ループで組み、逆行列を求める）は、テスト（`backend/tests/test_speedup.py`）に基準として残し、結果が許容誤差 1e-12 以内で一致することを確かめている
4. **探索の中で、同じ打順の評価を使い回す**（`optimizer.multi_restart_hill_climb`）：山登りは、リスタートをまたいで同じ打順を何度も評価する（手元の測定で、評価の約半分が重複）。1回の探索の中で、打順 → 期待得点 を覚えておき、同じ打順は計算し直さない。乱数の使い方と探索の道筋は変わらないので、乱数のシードを固定すると、使い回さない場合と同じ推奨打順になる（テストで確認）

高速化の効果と、計算結果が変わらないこと（キャッシュのあり・なしで案Aの差は 0、3・4 の前後で推奨打順は同じ）は、VALIDATION.md 8-2 にあります。全探索の時間は、測った条件を記録した値（VALIDATION.md 8-1）だけを使います。

## 5. 入力と検証のルール

この章では、入力する成績の項目と、入力を受け付けるかどうかの規則を説明します。規則はバックエンド（`backend/app/schemas/batter.py`）にあり、フロントエンドの入力フォームも同じ規則で検証します。

入力するのは、確率ではなく、一般的な回数の成績です。

| 項目 | 説明 |
|---|---|
| 打席数 (PA) | 必須（1以上） |
| 打数 (AB) | |
| 安打 (H) | |
| 二塁打 (2B) | |
| 三塁打 (3B) | |
| 本塁打 (HR) | |
| 四球 (BB) | |
| 死球 (HBP) | |
| 三振 (SO) | |
| 犠飛 (SF) | |
| 犠打 (SH) | 省略できる（省略すると 0） |
| 併殺打 (GIDP) | |
| 盗塁 (SB) | |
| 盗塁死 (CS) | |

犠打（SH）のほかは、API（`POST /lineup/evaluate`）で必須です。統計のキーは、JSON と API では `"2B"`・`"3B"`、Python の中では `doubles`・`triples` です。

| 区分 | 規則 |
|---|---|
| エラー（API は 422 を返す） | 各成績は 0 以上 20000 以下の整数／PA は 1 以上／AB ≤ PA／H ≤ AB／2B + 3B + HR ≤ H／SO + GIDP ≤ AB − H |
| 警告（計算は行い、レスポンスの `warnings` で知らせる） | AB + BB + HBP + SF + SH が PA と一致しない／PA が 200 未満（標本が小さい） |
| エラー（API は 400 を返す） | `input_order` が `batters` の ID と一致しない／9人でない／重複がある |
| エラー（API は 422 を返す） | `n_games` が 1〜200 の範囲外／打者 ID が空または65文字以上 |
| エラー（API は 422 を返す） | `display_names`（任意）の表示名が、前後の空白を除いて空または41文字以上／制御文字（改行・タブなど）を含む |
| エラー（API は 400 を返す） | `display_names` のキーが `batters` の ID と一致しない／前後の空白を除いた表示名に重複がある |

- 上限の 20000（各成績）と 200（`n_games`）は、統計的な根拠のある値ではなく、誤入力や悪用を防ぐための安全上の上限
- 打席数と内訳の合計が合わないことをエラーにしないのは、合わなくても計算はできる（イベント確率は合計1に正規化する）一方で、入力の誤りの可能性や、モデルの前提との関係を知らせる必要があるため
- 打席数が 200 未満の打者には、「標本が小さいので、確率の見積もりが実力からずれやすく、打順の結果も変わりやすい」という注意を出す。計算は止めない。**200 という値は本プロジェクトの目安で、出典・統計的な根拠はない**（何打席あれば十分かを示す値ではない）。値はバックエンドの定数 `LOW_PA_THRESHOLD` の1か所で決め、注意の文の中の数字もこの定数から作る。この注意は API だけが出し、フロントエンドは基準の値を持たない
- バックエンドとフロントエンドの検証の規則が一致することは、共通の入力例 `schemas/batter_stats_validation_cases.json` を両方のテストで使って確かめる
- リポジトリの選手データは、すべての規則をエラー・警告なしで通る（`backend/tests/test_validation.py`）
- フロントエンドの入力フォームは、入力の途中でも、規則ごとに必要な項目がそろえば矛盾を示す（例：打数と安打だけで H ≤ AB を判定する）。これは画面だけの動きで、全項目を入力した成績に対する結果（有効・無効、警告の有無）はバックエンドと同じ

### 5-1. 打者の ID と表示名

- 打者 ID（`batters` のキー、`input_order` の要素）は、打者を区別するための内部の値。画面では枠ごとに固定の ID（`b1`〜`b9`）を使い、画面には出さない
- 画面に出す名前は、リクエストの `display_names`（打者 ID → 表示名、省略できる）で渡す。指定すると、`warnings` の文は打者 ID ではなく表示名で作られる（画面の名前と注意の文の名前が食い違わないようにするため）。省略すると打者 ID を使う。レスポンスの `input_order`・`best_order` は、常に打者 ID で返す
- 表示名は、前後の空白を除いて1〜40文字（Unicode の符号位置の数）で、制御文字は使えず、打者どうしで重複できない。40文字は、画面の表示が崩れないための上限で、長い選手名に、同じ選手を複数の枠に入れたときの番号（「 (2)」など）を付けても収まる長さ。画面の既定の名前は「打者A」〜「打者I」で、空欄にすると既定の名前に戻す
- 表示名の規則の一致は、共通の入力例 `schemas/display_name_validation_cases.json` を両方のテストで使って確かめる

## 6. 出力と API

この章では、API が何を返すかを説明します。API の詳しい形は、バックエンドを起動したときの Swagger UI（`/docs`）でも確かめられます。

| エンドポイント | 内容 |
|---|---|
| `POST /lineup/evaluate` | 入力打順と推奨打順の期待得点、非効率%、損失点、案Bの参考値、注意（6-1） |
| `POST /batters/metrics` | 打者ごとの表示用の指標と注意（6-2） |
| `GET /presets`・`/presets/seasons`・`/presets/teams` | 選手データの一覧・シーズン・球団（6-3） |
| `GET /health` | 動作の確認（`{"status": "ok"}`） |

### 6-1. 期待得点の計算（`POST /lineup/evaluate`）

- 基本の値は「1試合あたりの期待得点」（`input_order_runs_per_game`・`best_order_runs_per_game`）
- 試合数ごとの合計は、`1試合あたりの期待得点 × 試合数` の単純な掛け算。1回の呼び出しで、143試合と162試合の合計を `totals_by_games` として返す（画面は、この値を切り替えて表示するだけで、計算し直さない）
  - 変わるのは試合数だけで、確率はMLBのデータ・文献の値のまま
  - リクエストの `n_games`（既定 143、1〜200）と、それに対応する `*_runs_n_games` もある
- **非効率%**（`inefficiency_percent`）：`(推奨打順の期待得点 − 入力打順の期待得点) ÷ 推奨打順の期待得点 × 100`
- **損失点**（推奨打順に対して、入力打順で少なくなる得点）
  - `runs_lost_per_game`：1試合あたり。`best_order_runs_per_game − input_order_runs_per_game`
  - `totals_by_games[].runs_lost`：試合数ごと。同じ要素の `best_order_runs − input_order_runs`
  - 推奨打順の期待得点は入力打順以上になる（4-1）ので、0 以上。入力打順と推奨打順の期待得点が同じなら 0
- **案Bの参考値**（`monte_carlo`）：入力打順を、設定した回数（既定 5000。環境変数 `MONTE_CARLO_TRIALS`。3-6）だけ試行して評価した `mean`（平均）・`std`（標準偏差）・`min`・`max`・`n_trials`（実際の試行回数）。推奨打順は案Bでは評価しない
- **注意**（`warnings`、文字列の配列）：計算はできるが知らせるべき点（打席数と内訳の合計の不一致、打席数が少ないこと）。種類は 6-2 の `PA_SUM_MISMATCH` と `LOW_PA` の2つで、文は 6-2 と同じ

### 6-2. 打者ごとの指標（`POST /batters/metrics`）

画面で打順を並べ替えるときの参考として、打者ごとの指標を返します。得点期待値の計算は行いません。画面に出す数値は API の値だけにする方針のため、指標はこの API で計算します。

- 入力：1〜9人分の成績（`batters`。検証の規則は5章と同じ）と、任意の `display_names`
- 出力：打者 ID ごとに、次の指標と、その打者についての注意
  - `warning_items`：種類つきの注意 `[{"code": 種類, "message": 文}]`。種類は `PA_SUM_MISMATCH`（打席数と、打数＋四球＋死球＋犠飛＋犠打の合計が合わない）と `LOW_PA`（打席数が `LOW_PA_THRESHOLD` 未満）の2つ。`PA_SUM_MISMATCH` は、入力検証の共通の例とフロントエンドの入力検証で使う名前と同じ
  - `warnings`：`warning_items` の `message` を同じ順に並べたもの（1回作った注意から両方を作るので、ずれない）。`POST /lineup/evaluate` の `warnings` と同じ文

| 指標 | 定義 |
|---|---|
| `PA`・`H`・`HR`・`SB`・`CS` | 入力の値のまま |
| `AVG`（打率） | H ÷ AB |
| `OBP`（出塁率） | (H + BB + HBP) ÷ (AB + BB + HBP + SF) |
| `SLG`（長打率） | 総塁打 ÷ AB（総塁打 ＝ 単打 ＋ 2×二塁打 ＋ 3×三塁打 ＋ 4×本塁打） |
| `OPS` | 出塁率 ＋ 長打率 |
| `BB_pct`（四球率） | BB ÷ PA |
| `SO_pct`（三振率） | SO ÷ PA |

- 分母が 0 で計算できない指標は `null` を返す（計算できて 0 になる場合と区別するため）。OPS は、出塁率か長打率のどちらかが `null` なら `null`
- 率は丸めずに返す。桁をそろえるのは表示する側
- wOBA・wRC+ は返さない（7-5）

### 6-3. 選手データの API

| エンドポイント | 返すもの |
|---|---|
| `GET /presets/seasons?league=mlb` | 選手データのあるシーズン（古い順） |
| `GET /presets/teams?league=mlb&season=2025` | 球団の一覧。リーグ（AL・NL）ごとに分け、リーグの中は地区（`division`。東 E・中 C・西 W の順）、地区の中は球団名の順。`count` はその球団を最終所属（`team_info.code`）とする選手の数。`team_info` の無い選手データは `without_team` に数える。地区の無い球団は `division` が `null` で、リーグの最後に並ぶ |
| `GET /presets?league=mlb&season=2025` | 全件（配列） |
| `GET /presets?...&team=NYY` | その球団を最終所属とする選手。`{"total": 総数, "items": [...]}`（名前の順） |
| `GET /presets?...&q=名前の一部` | 球団に関係なく、名前の一部で探す（大文字・小文字とアクセント記号は区別しない）。最大50件と総数（`total`）を返す |

- 各選手には、アプリが成績から計算した `summary`（AVG・OBP・SLG・OPS（小数第3位に丸める）、PA、HR、SB、CS、盗塁成功率 `SB_pct`）を付けて返す。OPS は、丸める前の出塁率と長打率を足してから丸める（丸めた2つを足すと1桁ずれることがあるため）
- `reference_metrics`（wOBA・wRC+ の公表値。7-5）は、書かれた値をそのまま返し、無ければ `null`
- 移籍した選手は、最終所属の球団だけに数え、移籍前の球団の一覧には出ない。名前で探せば見つかる
- `league` は選手データのフォルダ名（`data/presets/<league>/`）に使うため、英小文字だけを受け付ける。選手データの JSON の中の `"league": "MLB"` とは別の値
- 件数・応答の大きさ・時間の測定は、VALIDATION.md 7-4 にある

- **346件**：The SABR Lahman Baseball Database 1871-2025（readme の記載で Release Date: Dec 10, 2025）から、生成スクリプトで作ったもの（7-2）。計算した打席数（AB + BB + HBP + SF + SH）が 200 以上の選手。`verified` は `false`

### 7-2. Lahman からの生成方針

選手データを数百件の規模にするため、Lahman Baseball Database の CSV から選手データを作るスクリプト `scripts/build_lahman_presets.py` を用意しています。使い方は4つです。

| オプション | 内容 |
|---|---|
| `--dry-run` | 集計して報告するだけ |
| `--sample` | 固定のシードで選んだ選手の成績を表にするだけ（目視の照合用） |
| `--generate` | 選手データの JSON を作る |
| `--names-only` | 既存の選手データの `name` だけを、選手名の上書き（7-3）に合わせて書き換える |

- 元データ（`Batting.csv`・`People.csv`・`Teams.csv`）は、各自でダウンロードして `data/raw/lahman/` に置く。スクリプトはネットワークから取得しない。`data/raw/` は `.gitignore` でリポジトリから除いている
- ライセンス：readme には「This database is copyright 1996-2025 by SABR, via generious donation from Sean Lahman.」「This work is licensed under a Creative Commons Attribution-ShareAlike 3.0 Unported License.」と書かれている（原文のまま）。コードのライセンス（MIT）とは分け、`data/` の選手データにだけ当てはめる（表示は `data/NOTICE`、README のライセンスの節、画面の「データの出典」欄）
- CSV の形式（2025年版で確認）：`People.csv` と `Teams.csv` は先頭に BOM があり、`Batting.csv` には無い。スクリプトは `utf-8-sig` で読むので、どちらでも列名を正しく読める。列名は `Batting.csv` が playerID, yearID, stint, teamID, lgID, G, AB, R, H, 2B, 3B, HR, RBI, SB, CS, BB, SO, IBB, HBP, SH, SF, GIDP、`People.csv` に nameFirst・nameLast、`Teams.csv` に yearID・teamID・name がある
- 集計：`Batting.csv` の対象シーズンの行を、選手（`playerID`）ごとに合算する（同じシーズンに複数の球団に在籍した場合は、在籍ごとの行＝stint を足す）。合算する列は G, AB, R, H, 2B, 3B, HR, RBI, SB, CS, BB, SO, IBB, HBP, SH, SF, GIDP
- 空欄の扱い：どれか1つの stint で空欄の列は、合計を「欠損」とする（0 とはみなさない）。選手データに使う項目が欠損している選手は、候補にしない
- 打席数：Lahman には打席数の列がないため、`AB + BB + HBP + SF + SH` で計算する。公式の打席数には、捕手の打撃妨害による出塁なども含まれるため、計算した値と一致しないことがある（影響の大きさは未確認）
- 対象：計算した打席数が 200 以上の選手（投手の打席も記録に含まれるため、打席の少ない選手を除く）。打席数 200 以上の選手に投手が含まれるかは未確認（使った3つの CSV には守備位置の情報がなく、判別には `Appearances.csv`・`Pitching.csv` などが必要）
- 所属球団：stint の番号が最も大きい行の `teamID` を最終所属とし、移籍した選手もシーズンの合計を最終所属の球団に置く。在籍した球団の一覧（stint の順。続けて同じ球団が並ぶ場合は1つにまとめ、元の球団に戻った場合はもう一度並べる）も集計する。readme の BATTING TABLE には「stint          player's stint (order of appearances within a season)」と書かれている（原文のまま）
- 名前は `People.csv` の `nameFirst`・`nameLast`、球団名は `Teams.csv` の `name` を使う（接尾辞は 7-3 の上書きで足す）
- API と同じ入力検証（5章）を各選手に当てはめ、違反した選手を一覧にする
- 照合済みの2人（playerID が `judgeaa01`・`arraelu01`）は、生成の対象から除く（既存の2件のファイルは変えない）
- ファイル名と `id` は `<playerID>_<シーズン>`（例：`meadcu01_2025`）。照合済みの2件は `<名前>_<シーズン>`（`aaron_judge_2025`）だが、同じ名前の選手（Max Muncy が2人。`muncyma01_2025` と `muncyma02_2025`）がいても衝突しないよう、生成するものは playerID を使う。`name` は名前のままなので、同じ名前の選手データが2件ある（球団で区別する）
- `source` は、provider が「Lahman Baseball Database (SABR)」、url が Lahman の readme に書かれた Web サイト（https://sabr.org/lahman-database/）、`retrieved_at` が元データを取得した日。`note` に、機械的に生成し、独立した第二の出典との照合はしていないことと、使った版（readme の Release Date）を書く
- `team` と `team_info.name` は `Teams.csv` の `name` のまま、`team_info.league` は `lgID`、所属地区（`team_info.division`。E・C・W）は `divID`。複数の球団に在籍した選手には `teams_played` を付ける
- 同じ入力からは同じファイルになる（キーの順番、インデント2、改行は LF、末尾に改行1つ）

**球団コード**：Lahman の `teamID` は独自のコードで、一般的な略号と違うものがあります（2025年の例：New York Yankees は `NYA`、San Diego Padres は `SDN`、Los Angeles Dodgers は `LAN`、Chicago White Sox は `CHA`。`Teams.csv` の `teamIDBR` 列では、それぞれ `NYY`・`SDP`・`LAD`・`CHW`）。2025年の `Teams.csv` には30球団があります。選手データの球団コード（`team_info.code` と `teams_played[].code`）は、このプロジェクトで統一した表記にし、元の `teamID` は `team_info.lahman_id` に残します。`teamID` と違う表記にするのは次の13球団で、ほかの17球団は `teamID` のままです（対応表は `scripts/build_lahman_presets.py` の `TEAM_CODE_BY_LAHMAN_ID`）。

### 7-3. 選手名の接尾辞（表示名の上書き）

- `People.csv` には名前の接尾辞（Jr.・II など）の項目がないため、生成した選手データの `name` にも付かない。接尾辞を付ける選手と表記は、`data/overrides/display_names.json`（形式は `schemas/display_name_overrides.schema.json`）に書く。キーは playerID で、各項目に表示名（`name`）・確認した日（`checked_at`）・確認元の種類（`checked_source`）・補足（`note`、任意）を入れる
- 受け付けるのは、`People.csv` の名前の後ろに、半角スペースと半角 ASCII の接尾辞（`Jr.`・`Sr.`・`II`・`III`・`IV`）を足すことだけ。接尾辞より前の部分が元の名前と1文字でも違えば、スクリプトはエラーで止まる（アクセントつきの文字は元の表記のまま。例：Ronald Acuña Jr.）
- 生成（`--generate`）では、`People.csv` から作った名前に上書きを当てる。`--names-only` は元データを使わず、既存の選手データの `name` の行だけを書き換える。`name` 以外の行・キーの順番・ファイル名が変わる場合や、ファイルが生成スクリプトの書き出しの形でない場合は、何も書かずに止まる。2回続けて実行しても結果は同じ。上書きにあって選手データにない playerID は、警告として一覧に出す。照合済みの2件（`aaron_judge_2025`・`luis_arraez_2025`）は対象外
- 接尾辞を足したのは13人（Jr. が10人、II が2人、III が1人）。表記は作者が確認して手で入力した（確認元のサイト名などは記録していない）
- 同じ名前の別の選手を区別する画面の仕組み（打順に同じ表示名があるとき「 (2)」を付ける。`frontend/src/names.ts`）は、この上書きとは別のもの。Max Muncy の2人（`muncyma01`・`muncyma02`）は上書きの対象ではない

### 7-4. ファイルの形式とスキーマ

1人＝1つの JSON ファイルで、ファイルを足すだけで選手を追加できます。年度・リーグ別にフォルダを分け、ほかの年度やリーグを足しやすくしています。

```
data/presets/mlb/2025/
  ├── aaron_judge_2025.json
  ├── meadcu01_2025.json
  └── ...
```

- 各 JSON には、回数の成績と、メタ情報（年度・出典の URL・取得日など）だけを書く。打率・出塁率・長打率などの表示用の指標は、アプリが `stats` から計算する（`GET /presets` の `summary`。6-3）
- スキーマの実体は [`schemas/batter_preset.schema.json`](../schemas/batter_preset.schema.json)（この文書には転載しない）。すべての選手データがスキーマに合うことは、`backend/tests/test_preset_schema.py` と CI（`preset-validation`）で確かめる。件数が増えても速く検証できるよう、テストは検証器を1回だけ作って使い回す（測定は VALIDATION.md 7-4）
- スキーマの決まり
  - 一番上の階層と `reference_metrics` は、スキーマにないキーを受け付けない（キーの書き間違いを、無視せずにエラーにするため）
  - `stats.PA` は 1 以上（API の検証と同じ）
  - 任意の `team_info`（球団コード・球団名・リーグ・地区（`division`、E・C・W のいずれか、省略できる））と `teams_played`（複数の球団に在籍した選手だけ。2件以上、出場した順）がある。`teams_played` があるときは `team_info` も必要で、`teams_played` の最後の球団は `team_info.code` と同じでなければならない（スキーマでは書けないため `check_preset` で検査する）
  - `source` には任意の `note`（生成の方法や照合の状況などの補足）を書ける
  - `source.url` と `reference_metrics.source.url` は、`https://` で始まる URL だけを受け付ける（画面でリンクにするため）
- `verified: true` にする場合は、`source` に取得元の URL と取得日を正確に書く

### 7-5. wOBA・wRC+（公表値を参考として表示する）

wOBA・wRC+ は、API でもフロントエンドでも計算しません。公式の wOBA は故意四球を除きますが、このアプリの成績には故意四球の項目がなく、wRC+ は球場の補正が要るため、公表されている値と同じ定義では計算できないからです（FanGraphs "Guts!" の係数を使って計算する方式は採りません）。

- 公表値は、選手データの JSON の任意の欄 `reference_metrics` に書く。内容は、wOBA・wRC+（少なくとも一方）、対象シーズン、出典（出典名と `https://` で始まる URL）、取得日、備考（任意）
- 書いてよいのは、出典で確かめた公表値だけ。確かめていない値や仮の値は書かない（書いてあること自体が、出典で確認済みという意味になる）。`verified` は成績（`stats`）の確認の状況を表す欄で、参考値の確認の状況は表さない
- 対象シーズンは、選手データの `season` と同じ年でなければならない（`backend/tests/test_preset_schema.py` で確かめる）
- **この値はモデルの計算には使わない**。画面には「参考値（モデルの計算には使っていません）」と、出典・シーズンを添えて表示する。`reference_metrics` が無い選手データ、手入力の打者、選手データを読み込んだあとに成績を編集した打者には表示しない
- `GET /presets` は、書かれた値を計算も加工もせずにそのまま返す（無ければ `null`）
- 今の選手データには、まだ書かれていない

## 8. 画面の設計

この章では、画面の構成と、操作・表示の規則を説明します。画面がどの幅でも崩れないことや、コントラストの確認の結果は、VALIDATION.md 9章にあります。

### 8-1. 手順のタブ

- 3つの手順を、上部のタブ「成績の入力」「打順」「計算と結果」で切り替える（`frontend/src/components/StepTabs.tsx`）。入力欄（9人×15欄）が長く、1ページを上から見る作りでは打順や結果まで遠いため。順番に関係なく自由に行き来できる
- 部品の置き場所：成績の入力欄・選手データ・コピーは「成績の入力」、並べ替えと打者ごとの指標は「打順」、打席数が少ない打者の一覧・計算のボタン・結果は「計算と結果」
- 選んでいないタブのパネルは `hidden` で隠すだけで、アンマウントしない。入力した成績、打順、計算の結果、試合数の選択、開いている欄は、タブを切り替えても消えない
- WAI-ARIA のタブのパターンに従う：`role="tablist"`（名前は「手順」）・`role="tab"`・`role="tabpanel"`、`aria-selected`、`aria-controls`（タブ → パネル）、`aria-labelledby`（パネル → タブ）。切り替えはタブの選択の状態で伝わるので、`aria-live` は使わない
- キー操作：タブの上で ←/→ で前後のタブへ（端では反対側へ回る）、Home/End で最初・最後のタブへ。矢印で移ったら、すぐに切り替える。Tab キーで止まるのは選んでいるタブだけ（roving tabindex）で、次の Tab でパネルの中の部品へ進む
- 各パネルの末尾に「次へ（打順を決める）」「次へ（計算と結果を見る）」のボタンを置く（最後のパネルには置かない）。押すと次のタブに切り替え、そのタブにフォーカスを移す
- 切り替えたとき、ページがタブより下までスクロールしていたら、タブが画面の上端に来る位置まで戻す。ページの先頭付近にいるときは動かさない。フォーカスを移すときのブラウザのスクロールは止める（`preventScroll`）
- 計算を押したときに入力の誤りがあった場合と、エラーの要約の打者名を押した場合は、「成績の入力」のタブに切り替えてから、最初の誤りの欄にフォーカスする（隠れたパネルの中の欄にはフォーカスできないため）
- タブには手順の名前だけを出す。選んでいるタブは、色だけでなく、太字と下線（3px）でも分かる。押せる高さは 44px 以上

### 8-2. 成績の入力のカード

選手データから選ぶことを既定にし、自分で入力したいときだけ「手入力する」で入力欄を出します（`frontend/src/components/BatterCards.tsx`、`frontend/src/state/lineup.ts`）。初めは9人とも未選択です（成績は空。サンプルの値は入れていない）。

- カードの状態（`BatterSlot` の `mode` と `editing`。API に送る値の形と中身は、状態によらず同じ）
  - 未選択：打者の見出し（打者A など）と、「選手を選ぶ」（主）・「手入力する」（副）の2つのボタンだけ
  - 選手データ（要約）：選手データの情報（名前・年・「球団名 (コード)」、移籍した選手は「年間合計（複数球団）／在籍した球団：TB → CWS」のように球団コードで出場した順）と、AVG・OBP・SLG・OPS・HR・PA の要約。要約の数値は `POST /batters/metrics` の値で、まだ無いとき（読み込み中・取得に失敗したとき）は、編集していなければ選手データの `summary`、それも使えなければ「—」。ボタンは「編集する」「選び直す」「選択を外す」
  - 選手データ（編集中）：入力欄と表示名の欄を出す（読み込んだ値が入っている）。「編集を閉じる」で要約に戻る。成績を1項目でも変えると「（編集済み）」と出し、参考値（`reference_metrics`）を隠す。値を元に戻すか「選手データの値に戻す」を押すと、編集済みではなくなる。表示名は書き換えない
  - 手入力：入力欄と表示名の欄を出す。「選手を選ぶ」もある
- 誤りがあるとき
  - 「編集を閉じる」は、入力の誤り（表示名の誤りを含む）がある間は閉じない。ボタンは無効にせず、押したときに「誤りを直してから閉じてください。」と知らせ、まだ触れていない欄の未入力の誤りも出す
  - 未選択のカードがあるまま「期待得点を計算する」を押すと、入力エラーとして、そのカードとエラーの要約に「入力エラー：（打者名）：選手を選ぶか、手入力してください。」を出す。最初のエラーが未選択のカードなら、その「選手を選ぶ」ボタンへフォーカスを移す
  - 要約のカードの表示名がほかの打者と重複したときは、「「編集する」で名前を直せます。」を添える。エラーの要約から移るときは、そのカードの「編集する」ボタンへ移す（入力欄が無いため）
- 上書きの確認：選手データを読み込むとき、入力した値が消える場合（手入力の値、または選手データを編集した値）だけ確認を出す。編集していない選手データを選び直すときは確認しない
- コピー：コピーの操作は、入力欄を出しているカード（手入力・編集中）にだけ出し、コピー元に選べるのもそれらのカードだけ。「この打者の成績を、ほかの打者にコピー」のコピー先は、要約のカードを除いた全員（要約のカードは、選手データを上書きしてしまうため、コピー先にしない）。未選択のカードはコピーすると手入力になり、編集中のカードも選手データとの結びつきを外して手入力になる。ほかの打者からコピーした成績は手入力の扱いで、選手データの情報や参考値は写さない
- フォーカスの移し方：選手を読み込んだあとは、そのカードの「編集する」ボタン（ダイアログが閉じたあと）。「手入力する」「編集する」は表示名の欄。「編集を閉じる」は「編集する」ボタン。「選択を外す」は「選手を選ぶ」ボタン（「選択を外しました。」と知らせる）
- ボタンの読み上げの名前には打者名を入れる（「打者Aの選手を選ぶ」「打者Aを手入力する」「打者Aを編集する」「打者Aの選手を選び直す」「打者Aの選択を外す」「打者Aの編集を閉じる」）。ボタンの高さは 44px 以上
- 入力欄の項目名は、列の幅に収まらないときは最大2行で折り返す（略号「GIDP」などは途中で折り返さない）。同じまとまり（1行に最大4項目）の項目名の高さを CSS の subgrid でそろえ、入力欄の上端をそろえる。subgrid が使えないブラウザでは、項目ごとに縦に並ぶ

### 8-3. 選手を選ぶダイアログ

（`frontend/src/components/PresetDialog.tsx`）

- 「選手を選ぶ」で、ブラウザ標準のダイアログ（`<dialog>`）を開く。ダイアログの名前も「選手を選ぶ」。シーズン（既定は最新）→ 球団（リーグ → 東地区・中地区・西地区ごと、地区の中は球団名の順、選手数つき）→ 選手（名前の順。打率・出塁率・長打率・OPS・本塁打・打席を API の値で表示）の順に選ぶ。名前での検索（すべての球団）も使える
- 選手の一覧は、HTML の上では選んだ球団のボタンの直後に置く（ボタンは `aria-expanded` と `aria-controls` で開いた一覧を示す）。キーボードでも読み上げでも、球団のボタンの次に選手が続く。狭い画面ではボタンの下に出し、広い画面では CSS（`position: absolute`）で見た目だけ右側の列に出す。検索の結果は検索欄の直後に出す
- 検索の入力欄の幅は 16em で、ダイアログの中の幅より広くしない（`width: min(16em, 100%)`）
- Esc キーは、ブラウザ標準の動き（`cancel` イベント）に加えて、ダイアログの中で押されたキーも直接受け取って閉じる
- 入力済みのカードに読み込むときは、ダイアログの上に確認のダイアログ（`role="alertdialog"`）を重ねて「打者Aの入力を上書きします。よろしいですか？」と確かめる。Esc キーとキャンセルは確認だけを閉じ、フォーカスを選んでいた選手の「読み込む」ボタンへ戻す。同じ選手を別のカードにも読み込むと、表示名に「 (2)」などを付ける
- **続けて次の打者を選ぶ**：ダイアログの「読み込み先：打者X」の下にスイッチ（`<input type="checkbox" role="switch">`）を置く。初めはオンで、値はページを開いている間だけ保つ（ブラウザには保存しない）
  - オン：読み込んでもダイアログを閉じず、読み込み先を次の未選択の打者（今の読み込み先より後ろで最初の未選択の打者。いなければ先頭から探す）へ移す。選んでいた球団・選手の一覧・検索はそのまま残す。ダイアログの中の知らせ（`role="status"`）に「打者Cに（名前）を読み込みました。読み込み先は打者Dです。」と出す。未選択の打者が残っていなければ、ダイアログを閉じて「9人の選手がそろいました。」と知らせる
  - オフ：読み込むとダイアログを閉じる
  - 続けて選べるのは、未選択のカードの「選手を選ぶ」から開いたときだけ。「選び直す」や、手入力・編集中のカードから開いたときは、1人読み込んだら閉じる。このときはスイッチを出さず、「1人を読み込むと、この画面を閉じます。」と出す（押せない部品を出すより分かりやすいため）
  - 「閉じる」ボタンと Esc キーは、いつでも使える
- **入れ替え**：読み込み先がすでに選手データを読み込んでいるときは、読み込み先の行に「（入れ替え）」を付け、閉じたあとのカードの知らせを「（前の選手名） を （新しい選手名） に入れ替えました。」にする。手入力のカードに読み込むときは「（表示名）に （新しい選手名） を読み込みました。」。どちらも1人で閉じるため、ダイアログの中には入れ替え用の文を出さない
- **読み込めたことの表示**：読み込んだ選手の行の下に「✓ 打者Aに読み込みました」と出す（✓ は `aria-hidden`）。ダイアログを閉じるまで残す。読み上げは、知らせの領域ではなく、その行の「読み込む」ボタンの説明（`aria-describedby`）に結びつける（二重に知らせないため）
- **押した行の位置を保つ**：読み込むと、上の知らせや行の下の表示で高さが変わる。ダイアログが一番上にあるときは、ブラウザのスクロールの自動調整が働かず、押した行が下へずれるため、押す前のボタンの位置を覚えておき、描画の直後（`useLayoutEffect`）にスクロール位置をその差だけずらす
- テストの環境（jsdom）は `<dialog>` の `showModal` を実装していないため、テストでは開閉だけを置き換えている

### 8-4. 打順の並べ替え

（`frontend/src/components/OrderList.tsx`）

- 「打順」のタブで、上から1番〜9番の順に並べ替える。並べた順番が、そのまま計算の `input_order` になる。カードの並びは変わらない
- 操作は3通りで、どれでも同じ結果になる。ドラッグが使えない環境やスクリーンリーダーでも、ボタンと番号の指定だけですべての操作ができる
  - ドラッグ：各行の取っ手（⋮⋮）を持って動かす。マウス・タッチ（`PointerSensor`）とキーボード（`KeyboardSensor`。スペースかエンターで持ち上げ、上下の矢印キーで動かし、もう一度スペースかエンターで置く。エスケープでやめる）。説明と、持ち上げ・移動・終了・中止の読み上げは日本語で用意した
  - 「上へ」「下へ」：1つずつ動かす。1番の「上へ」と9番の「下へ」は押せないが、フォーカスはでき、理由が読み上げられる（`aria-disabled` と `aria-describedby`）
  - 「移動先」と「移動」：番号（1〜9）を選んで、その番号へ動かす。間の打者は順番を保ったまま詰める
- 並べ替えたあとは、動かした打者の同じ操作にフォーカスを戻し、「打者Cを3番から1番に移動しました。」と知らせる（ドラッグのときは dnd-kit が同じ内容を読み上げるので、二重にならないよう知らせない）
- 各行には、`POST /batters/metrics` の指標と、その打者についてのすべての注意（API の文のまま）を出す。指標は AVG → PA → H → HR → OBP → SLG → OPS → K% → BB% → SB の順。画面には略号、読み上げには日本語の名前を使う。計算できない値（`null`）は「—」。率は「.278」の形、K% と BB% は API の割合（0〜1。例：0.215）を「21.5%」の形（小数点以下1桁のパーセント）にする（表記をそろえるだけで、新しい値は作らない）。成績がそろって検証を通った打者だけを送り、入力が止まってから 300ミリ秒後に呼ぶ。表示名に問題がある間は、注意の文に正しい名前を出せないので呼ばない。選手データを読み込んで編集していない打者には、参考値（`reference_metrics`）も出す
- 指標の状態の文は、一覧の上に1回だけ出す（`role="status"`）。指標が出る前の行には、見えない仮の一覧（`visibility: hidden`）を置き、指標が出る前後で行の高さを変えない
- ドラッグの部品には dnd-kit（`@dnd-kit/core` 6.3.1、`@dnd-kit/sortable` 10.0.0、`@dnd-kit/utilities` 3.2.2。いずれも MIT ライセンス）を使う。マウス・タッチ・キーボードでのドラッグと、読み上げの仕組みを1つの部品でそろえられるため。peer 依存は `react >=16.8.0`
- **注意**：dnd-kit のこれらの版の最終公開は 2024年12月（`@dnd-kit/utilities` は 2023年11月）で、更新が止まっている可能性がある（npm の公開日からの見立て）。後継の `@dnd-kit/react`（0.x）は安定版ではないため使っていない。React を大きく更新するときは、動きを確かめ直す必要がある。ボタンと番号の指定だけですべての操作ができるので、ドラッグが動かなくなっても並べ替えはできる

### 8-5. 結果の画面

（`frontend/src/components/ResultSummary.tsx`）

- 「計算と結果」のタブの先頭に、「打席数が少ない打者」の一覧を出す。対象は、API の種類つきの注意（`warning_items`）で `code` が `LOW_PA` の打者だけで、文は API のまま。基準の打席数による判定は、フロントエンドでは行わない
- 計算したあとに成績・表示名・打順を変えると、前の結果を消し、「成績・表示名・打順が変わったため、前の計算結果は消しました。もう一度「期待得点を計算する」を押してください。」と出す
- 結果は、上から順に、試合数の切替、非効率% と損失点、2つの打順の一覧
- **試合数の切替**：「143試合」「162試合」のラジオボタン（既定は143試合）。選択肢は API の `totals_by_games` から作り、合計は `totals_by_games` の値をそのまま出す（フロントエンドで掛け算をしない）。選んだ試合数は、計算し直しても保つ。注記（「試合数のみの切替で、確率はMLBデータ・文献値のままです（…）」）は「説明」のボタンの中に置く
- **非効率% と損失点**：非効率%（`inefficiency_percent`）を上の目立つ位置に大きく出し、その下に「入力打順だと、推奨打順より、1試合あたり ○ 点・選んだ試合数で ○ 点少なくなります」と損失点を出す（`runs_lost_per_game` と、選んだ試合数の `totals_by_games[].runs_lost`）。損失点が 0 のときは「入力打順と推奨打順の期待得点は同じです」。非効率% の定義の文は「説明」のボタンの中に置く
- **2つの打順の一覧**：「入力打順」と「推奨打順（近似探索）」を、画面の幅にかかわらず左右に並べる（HTML の順番でも入力打順が先）。それぞれの上に、1試合あたりの期待得点と、選んだ試合数の合計を出す。近似探索の注意（「推奨打順は近似探索で求めたもので、最も期待得点が高いとは限りません。」）を常に出し、詳しい文は「説明」のボタンの中に置く
- 各行は、打順の番号・表示名と、指標（AVG・OBP・SLG・OPS・HR・SB。狭い列では AVG・OPS・HR・SB の4つ。`POST /batters/metrics` の値）。各行は固定の構造にして、どの打者でも同じ高さにする。1行目は「番号・表示名・札」で折り返さず、札は縮めず切らず、収まらないときは名前の側を「…」で省略する。文字は 0.75rem（12px）以上
- **動いた打者の札**：推奨打順の各行に、入力打順から動いたことを示す札を付ける。広い列は行の右端に「3番→1番」、狭い列は名前のすぐ後ろに「元3番」。札は見た目だけ（`aria-hidden`）で、読み上げは「入力打順の3番から1番へ」の1文。動かなかった打者は、読み上げ用の文字で「変更なし」と伝える。札は、API が返す2つの打順（`input_order` と `best_order`）の位置を比べるだけで、新しい値は作らない
- **列の幅による切り替え**（CSS の container query。container は各行 `li`）。切り替えの幅は Edge で測って決めた
  - 列の幅 255px 以上：フルネームと「9番→1番」の札。それ未満は短い名前と「元9番」の札。根拠：「9番 Pete Crow-Armstrong 9番→1番」の1行目の幅が 254.5px
  - 列の幅 200px 以上：指標6つを3列×2段。それ未満は OBP・SLG を外し（`display: none` で、画面からも読み上げからも外す）、4つを2列×2段にし、指標の文字を 0.75rem にする（OPS が1以上（例「OPS 1.201」）でも、幅 320px で枠に収まるように）。根拠：最も広い指標（AVG .306）が 53.8px で、3列と間隔 8px×2 で 177.4px。OPS が 1 以上で1桁多くなる分を見込んで 200px にした
  - 列の幅 344px 以上：指標6つを6列×1段。根拠：指標の幅の合計と間隔 12px×5 で 335.4px。同じく1桁多くなる分を見込んだ
  - 文字の幅はフォントによって変わる。container query が使えないブラウザでは、狭い列の表示になる
- **短い名前**（狭い列だけ。`frontend/src/format.ts` の `shortDisplayName`。表示だけの整形で、表示名のデータは変えない）：最初の単語をイニシャルにする（例：Aaron Judge → A. Judge、Ronald Acuña Jr. → R. Acuña Jr.、Max Muncy (2) → M. Muncy (2)）。対象は、空白で区切られた2語以上で、最初の単語がラテン文字で始まり、残りに接尾辞以外の単語がある名前だけ。見た目の名前は `aria-hidden` にし、フルネームを `title` と読み上げ用の文字で1回だけ伝える
- **行の位置をそろえる**：2つの一覧の同じ番号の行は、同じ高さ・同じ位置にそろえる。外側を12行（見出し・期待得点・9人・シミュレーションの欄）の CSS グリッドにし、各列と各一覧を `subgrid` にして行を共有する（見出しが片側だけ2行に折り返したときもそろう）。HTML の構造と順番、キーボードの移動の順、読み上げの順は変えない。`subgrid` が使えないブラウザでは各列が独立して縦に並び、狭い画面で見出しが2行になると、推奨打順の側が1行分下がる
- 幅 800px 未満では、一覧の上の期待得点を縦に並べ、枠の内側の余白と列の間隔を小さくする
- **参考：シミュレーション**：入力打順の一覧の下に、たたんだ欄を置く（初めは閉じる）。API の `monte_carlo` の `mean`・`std`・`n_trials` だけを「（n_trials）試合の1試合あたりの得点：平均 ○、標準偏差 ○」の形で出す（試行回数はサーバーの設定で変わるので、決めて書かず、API の値を出す。既定では「5000試合…」）。最小・最大は、極端な1試合が目立って誤解を招くおそれがあるため出さない。乱数を使うため計算のたびに少し変わること、上の期待得点（案A）とほぼ一致するかを確かめる参考値であること、推奨打順は評価していないことを書く

### 8-6. 文章と「説明」のボタン

### 8-7. 見た目

  - 帯は `<main>` の中のまま、`box-shadow: 0 0 0 100vmax` で左右に伸ばし、`clip-path: inset(0 -100vmax)` で上下を切る（影はスクロールの範囲に含まれないので、横スクロールが出ない。`100vw` は、スクロールバーの幅の分だけ横スクロールが出る環境があるため使わない）
- **文字**：システムのフォント（`system-ui` を先頭にし、使えないブラウザでは Segoe UI・Hiragino Sans・Yu Gothic UI・Meiryo などの標準のゴシックの順に探す）。基本は 16px、見出しは 700、補足は 0.875rem でグレー
- **パネルの見出し**：太字・1.25rem で、左に紺の縦線（幅 4px、高さ 1em、角を 2px 丸める。疑似要素なので読み上げには含まれない）。縦線と文字の間は 0.6rem。見出しの前の余白は 32px、見出しと案内の文の間は 4px で、見出し → 案内の文 → 「説明」のボタンをひとまとまりに見せる
- **数字**：期待得点・損失点・非効率%・指標は、太字（700）の等幅数字（`tabular-nums`）。略号（AVG など）は太くしない。単位が元の文にあるところ（非効率% と K%・BB% の「%」、損失点の文の「点」、試合数の選択肢の「試合」）だけ、その文字を `<span class="unit">` で包み、小さく（約 0.6倍）・太さ 400・補足の色にする（文字列そのものは変えない）。期待得点（4.100 など）は元の文に単位が無いので包まない。1試合あたりの期待得点と非効率% は、幅 800px 未満 28px、以上 32px。試合数の合計は 1.5rem
- **部品**
  - 主のボタン（選手を選ぶ・編集する・計算する など）は、ほぼ黒のピル型。副のボタン（手入力する・コピー・上へ など）は、地を塗らず、枠線と本文の色の文字のピル型（主と副は、面の有無で分かる）
  - 試合数の選択肢は、押せる高さ 44px のピル型にし、選んだものを、ほぼ黒の面と白い文字と太字にする。ラジオボタンの丸は残す（色だけでなく、丸と太字の形でも分かる）。開いている球団のボタンも同じ
  - エラーと注意は、文言の接頭辞（「入力エラー：」「注意：」）に加えて形でも区別する：入力欄の下の行は、エラーが四方の枠、注意が左の太い線。バナーは、エラーが四方の 2px の枠、注意が細い枠と左の 4px の線
  - フォーカスの枠は 3px の `accent`。動きは、ボタン・選択肢の色の切り替え（0.15s）だけで、`prefers-reduced-motion: reduce` では、すべての切り替えとアニメーション（ドラッグの並べ替えの動きを含む）を 0 にする
- **コントラスト**：`npm run contrast` で、ライト・ダークのそれぞれについて、文字（4.5:1 以上）と部品（3:1 以上）の32の組み合わせを確かめる（結果は VALIDATION.md 9-2）。装飾の部分も 3:1 以上を確かめていて、見出しの縦線とページの地はライト 7.56:1・ダーク 8.38:1、タイトルの印と帯はライト 13.32:1・ダーク 16.82:1

## 10. モデルの限界

この章では、モデルが扱っていないことと、その影響を説明します。結果は、これらの簡略化を前提にした目安です。

### モデル全般の限界

- 相手投手の影響（左右・調子・対戦成績によるプラットーン効果）は反映しない。全打席を平均的な対戦環境として扱う（シーズンで換算するため、平均的には均されると考えられる）
- 守備・守備位置・シフトは考慮しない
- 走塁は盗塁（一塁→二塁）だけをモデル化する。三盗・本盗は対象外
- 走者の進塁の能力は打者の個人差を反映せず、リーグ平均の進塁確率（2003年のデータ）を暫定で使う。打者の成績（2025年）と年代が違う
- 単打での一塁走者と二塁走者の進塁は、走者ごとの進塁確率を別々に引き、二塁走者が三塁で止まったときだけ一塁走者を二塁で止める近似である。2人の走者の進塁の結びつき（前の走者が止まると後ろの走者も止まりやすい、など）を、データから求めたものではない
- 打球アウトによる進塁・生還は扱わない（内野ゴロでの生還、0・1アウトでのフライでのタッチアップ進塁など）。この簡略化が、得点を少なめに見積もる主な原因らしいことを、VALIDATION.md 5章で確かめている
- 相手の守備範囲・エラーは考慮しない
- 敬遠は通常の四球と区別しない
- 犠打は成功する場合だけをモデル化する（失敗・セーフティバント・スクイズに特有の分岐は考慮しない）
- 打順は固定とし、シーズン中の交代・けが・打順の変更は考慮しない
- 各打席のイベント確率は独立で同じ分布と仮定する（調子の波などは反映しない）
- 采配（バント・敬遠・代打・盗塁の判断など）は考慮せず、機械的に確率を当てはめる
- シーズンを通して確率が一定と仮定する（シーズン内の変動や年齢による衰えなどは反映しない）
- パークファクターによる補正は行わない
- 打席数が少ない打者も、入力された成績をそのまま確率に使う（標本が小さいことによる不確かさの補正や、平均への回帰は行わない）。打席数が 200 未満の打者には注意を出すが、200 は本プロジェクトの目安で、出典・統計的な根拠はない（5章）

### 日本のプロ野球に当てはめる場合の注意

モデルはMLBのデータで作っているため、日本のプロ野球の選手や試合にそのまま当てはめると、精度が落ちる可能性があります。使用球（反発の違いによる長打の出やすさ）、球場の大きさ・パークファクター、指名打者の制度、試合数（143試合の切替は、試合数を掛けるだけで確率は変えない）、延長戦や引き分けの規則の違いは、モデルに入っていません。

### 指標についての補足

Statcast の x系指標（xBA、xwOBA など）は「運を除いた実力の評価」を目的とした指標で、実際の結果とあえてずれるように設計されているため、モデルの入力には使いません（モデルは、実際に起きた結果に基づく回数の成績を使います）。

## 11. 今後の拡張候補

この章では、今は扱っていないが、今後の候補として考えていることを挙げます。

- 進塁確率のデータを、打者の成績と同じ年度で、より詳しい状況別（打球の方向別など）のものに差し替える

- アウト時の進塁（三塁走者の生還に限らず、二塁→三塁・一塁→二塁なども含む）を、独立した打席単位のデータ（例：Retrosheet）から求めて、まとめてモデル化する（VALIDATION.md 5-3 の診断を参照）

- Statcast の x系指標を使った、別のシミュレーションの方式
- 対戦投手を考慮したプラットーン効果の反映
- パークファクターの補正
- 全打順の探索のベクトル化と、バックグラウンドでの処理
- 画面の入力内容をブラウザに保存する（再読み込みしても消えないようにする）
